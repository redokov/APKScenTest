```

       скан документов → фикстуры → .feature (шаблоны + ПАТЧИ в 1С)
```

### Дополнение T1-аудита (28/29.10, полная таблица — в отчёте ночи)

- **Python-зависимостей в BSL-механике не найдено**: ObjectModule препроцессора чистый
  (файлы/JSON/запросы/ПользователиИБ); единственные ОС-вызовы — Windows-COM
  (`WScript.Shell`: запуск 1cv8c TestManager, taskkill, powershell-зачистка
  осиротевших TestClient, ping-паузы) в модулях форм — воспроизводимы в чистом 1С
  на Windows.
- **Найденная python-зависимость вне BSL (заводим задачу на живую часть T5)**:
  создание/удаление neg-пользователя (`create_neg_user` в t8_gate.py:479-551 —
  5 ролей + регистрация в справочнике Пользователи) — перенести в раннер EPF
  (серверный код); инверсия вердикта и neg-шаблон уже в BSL/комплекте.
- **Манифест-манипуляции** (allowlist REAL_TEMPLATES, smoke под 1-го автора,
  вставка neg-фичи, drop из манифеста — `prepare_real_manifest`) — перенести в
  препроцессор/раннер EPF (живая часть, вместе с neg-пользователем).
- **Формат per-scenario результатов** (allure `<build>/*-result.json`):
  `name/status/start/stop` есть; поля `user` в allure НЕТ — берётся из
  `ИмяСборки`/батча (уже делает BSL `СобратьОтчет` → summary.json:
  `scenario, user, status, durationMs, batchStatus, returnStatus, negative`).
- **baseline-real.json**: ключ (scenario, user) → status; `totals` — справка;
  сравнение только по `scenarios[]`.
- **Хардкод в раннере**: `ПрочитатьЗадание`/`ЗаписатьАртефакт` пишут пути
  `tmp/t6/runner_task.json|runner_result.json` — параметризовать при T4.

## Technical Decisions (проектные решения к обсуждению)

### TD-001 (Q-1): данные патчей — файл JSON в комплекте, алгоритм — в препроцессоре

- **Decision:** патчи хранятся в `scenarios/scenario-patches.json` (та же
  семантика block/replace/drop, что в `SCENARIO_PATCHES`), препроцессор
  читает файл (ЧтениеJSON) и применяет к тексту шаблона при генерации.
- **Why:** правка сценариев = правка файла данных, без пересборки EPF;
  формат уже обкатан python-стендом (офлайн-проверка показала 1-в-1
  воспроизведение диагностических кандидатов); переносимость комплекта.
- **Alternatives:** макет в EPF (пересборка на каждую правку сценария);
  справочник в базе (теряется переносимость).

### TD-002 (Q-2): baseline — JSON-файл комплекта

- **Decision:** `scenarios/baseline.json` (ключ `сценарий|пользователь` →
  статус), раннер читает/сравнивает/обновляет (явная команда «зафиксировать
  эталон», доступна только при зелёном прогоне).
- **Why:** переносимость (база не хранит эталон); формат
  `baseline-real.json` уже существует.
- **Alternatives:** регистр сведений в базе (живёт с базой, но не
  переносится между стендами).

### TD-003 (Q-3): отчёт — форма раннера с таблицей результатов

- **Decision:** таблица результатов на форме раннера (колонки: сценарий,
  пользователь, статус, vs baseline, сек) + панель вердикта и маркеров
  парольной безопасности; выгрузка таблицы в файл — кнопка (опция).
- **Why:** «раннер показывает в сессии, откуда запускался» (требование
  пользователя) — минимум UI-работы при максимуме читаемости.
- **Alternatives:** отдельная форма-отчёт с детализацией по шагам VA
  (больше работы; детализация шагов уже есть в логах VA/Allure).

### TD-004 (Q-4): neg-батч — переупаковка существующей BSL-механики

- **Decision:** механика neg (состав роли, временный пользователь,
  инверсия вердикта) остаётся как есть (спека 004, BSL), раннер включает
  neg-батч в общий цикл и отчёт. Аудит T1 подтверждает отсутствие
  python-зависимостей; при находке — точечный перенос.

### TD-005: исходники раннера канонизируются в `src/АпкРаннер`

- **Decision:** финальные исходники раннера (сейчас `tmp/t*/runner_src`)
  переносятся в `src/АпкРаннер/`, сборка — штатным epf-build; `tmp/`
  перестаёт быть источником истины.

## Риски / открытые места

- Чтение результатов батчей раннером сегодня завязано на файлы
  result-JSON VA — проверить полноту полей для отчёта-формы (статусы
  батчей есть; по-сценарные статусы читаются из отчёта VA) — аудит T1.
- Компонента Vanessa (VanessaExt) должна быть установлена на стенде
  заказчика — инструкция (FR-010), не автоматизация.
- `1cv8c TESTMANAGER`-сеансы VA стартуют как отдельные процессы: раннер
  уже умеет (спека 001, TD про PID/таймаут), поведение сохранить.

## План валидации

1. Офлайн: генерация фич препроцессором == эталон python-стенда
   (diff сценариев на фикстурах dev_erpapk_demo) — перенос патчей 1-в-1.
2. Приёмка комплекта: ручной прогон на копии базы без python
   (препроцессор → раннер → отчёт-форма) — зелёный, пароли восстановлены.
3. Smoke отрицательного пути: отмена раннера посреди прогона → хэши
   восстановлены (FR-006).
