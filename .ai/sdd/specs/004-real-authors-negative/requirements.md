## Overview

Расширение регресс-конвейера APKScenTest до исходной цели продукта
(steering product.md): сценарии выполняются **под правами реальных
пользователей — авторов документов**, а не только под временными зондами.
Плюс негативное покрытие: пользователь **без полных прав** получает
ожидаемую ошибку там, где полный прогон проходит.

Релиз 2 по решениям ретро (PLAN.md Фаза 5): (а) реальные авторы
(снятие D-001 спеки 002) + (д) негативные сценарии. Животноводство,
планирование, arm-fuel-expense для авто-ПЛ — бэклог.

## User Stories

### US-1: Регресс под реальными авторами

**Как** инженер по качеству ERP+АПК,
**хочу** запускать регресс-сценарии под реальными пользователями
(авторами документов: ОрловАВ, СоколовМИ и др., как их находит
препроцессинг),
**чтобы** прогон проверял не только функциональность, но и права/RLS
реальных пользователей — то, что не покрывают зонды с ПолнымиПравами.

Acceptance criteria:
- Прогон выполняется с манифестом, где пользователи батчей — реальные
  авторы документов (из fixtures), зонды не создаются (или создаются
  только для smoke, если нужно).
- Хэши паролей реальных авторов восстанавливаются при любом исходе
  (механизм спеки 001: snapshot → тестовый пароль → прогон → restore,
  включая отказные ветки).
- Отчёт различает пользователей: пользователь батча = реальный автор,
  и это видно в regress-report.md и baseline-сравнении.

### US-2: Негативный сценарий «нет прав»

**Как** инженер по качеству,
**хочу** в прогоне участвует пользователь без полных прав (ограниченная
роль), для которого операции документов недоступны,
**чтобы** фиксировалась ожидаемая ошибка доступа (сценарий проходит,
если ошибка воспроизведена корректно) — это ловит поломки RLS/прав.

Acceptance criteria:
- В прогоне есть негативный пользователь и негативные сценарии
  (ожидаемая ошибка вместо успешной записи).
- Негативный сценарий помечается как «ожидаемый отказ»; фактическая
  ошибка ≠ ожидаемая = FAIL.
- Негативный пользователь — временный (создаётся/удаётся прогоном),
  его права задаются ролью без ПолныхПрав.

### US-3: Безопасность и окно прогона

**Как** владелец демо-базы,
**хочу** подмена паролей реальных авторов происходит только на время
прогона, в тихие часы, с гарантией восстановления,
**чтобы** реальные пользователи не пострадали и не заметили подмену.

Acceptance criteria:
- Прогон с реальными авторами запускается только специальным флагом
  (не по умолчанию).
- Перед прогоном: проверка, что база не используется (нет чужих сессий
  реальных авторов) — предупреждение/отказ, если авторы онлайн.
- После прогона (и любого сбоя): хэши восстановлены; в отчёте —
  факты восстановления per-user (pwd=True как у зондов сейчас).
- В runbook: процедура и меры предосторожности.

## Functional Requirements (EARS + MoSCoW)

### FR-001: Режим реальных авторов в регресс-команде — Must Have

WHEN администратор запускает регресс-команду с флагом реальных авторов
THE SYSTEM SHALL сформировать батчи по манифесту с реальными авторами
документов (без ограничения restrict на зонды), подменить пароли авторов,
выполнить гейт и восстановить пароли
SO THAT прогон проверяет права/RLS реальных пользователей.

### FR-002: Восстановление хэшей реальных авторов при любом исходе — Must Have

WHEN прогон с реальными авторами завершился (успех, ошибка, прерывание)
THE SYSTEM SHALL восстановить сохранённые хэши паролей всех авторов
и подтвердить это в отчёте per-user
SO THAT реальные пользователи не затрагиваются после прогона.

### FR-003: Отказ при онлайн-авторах — Must Have

WHEN перед прогоном с реальными авторами кто-то из авторов имеет активную
сессию в базе
THE SYSTEM SHALL отказаться от прогона до подмены паролей (exit 2, база
и пароли не тронуты) с перечнем онлайн-авторов
SO THAT подмена не затрагивает работающих пользователей.

### FR-004: Негативный пользователь и негативные сценарии — Must Have

WHEN прогон (в режиме реальных авторов) формирует манифест
THE SYSTEM SHALL включить временного негативного пользователя (роль без
полных прав) и негативные сценарии (ожидаемая ошибка), выполняемые
под ним
SO THAT проверяется RLS/права.

### FR-005: Вердикт негативного сценария — Must Have

WHEN негативный сценарий выполнен
THE SYSTEM SHALL засчитать PASS, если воспроизведена ожидаемая ошибка
доступа, и FAIL — если операция неожиданно прошла или ошибка другого типа
SO THAT «нет прав» = покрытие, а не ложный зелёный.

### FR-006: Отчёт с реальными авторами — Should Have

WHEN прогон с реальными авторами завершён
THE SYSTEM SHALL отразить в отчёте пользователей-авторов (не зондов),
факты восстановления паролей и разделение позитив/негатив сценариев
SO THAT инженер видит, под кем и что проверено.

### FR-007: Baseline режима реальных авторов — Should Have

WHEN прогон с реальными авторами зелёный
THE SYSTEM SHALL позволить зафиксировать его как baseline этого режима
(отдельный от зонда-baseline, ключ (scenario, user) сохраняется)
SO THAT сравнение режима с самим собой осмысленно.

### FR-008: Runbook релиза 2 — Should Have

THE SYSTEM SHALL пополнить `docs/runbook.md` режимом реальных авторов:
флаг, окно прогона, проверка онлайн-авторов, восстановление при сбое.

### FR-009: Повтор веб-прогона T7 — Could Have

WHEN лицензия среды позволяет ≥3 одновременных сеанса
THE SYSTEM SHALL повторить rehearsal-прогон веб-клиентом (механика спеки
003 уже готова) и закрыть T7
SO THAT веб-клиент покрыт регрессом. (Заблокировано лицензией; вне
контроля кода.)

## Non-Functional Requirements

### NFR-001: Performance (наследие 003)

- Гейт ≤ 40 мин (NFR-001 спеки 003); полный цикл с baseline-dt ≈ 47 мин
  ± рост от большего числа батчей (реальные авторы + негативный
  пользователь) — измерить, зафиксировать фактом.

### NFR-002: Security / данные

- Подмена паролей — только временная, только на демо-базе, только через
  механизм спеки 001 (СохраняемоеЗначениеПароля), восстановление в
  finally-семантике; никакой фиксации тестовых паролей в отчётах/git.
- Негативный пользователь — временный, удаляется прогоном; его пароль
  неизвестен реальным людям и не попадает в артефакты.

### NFR-003: Reliability

- Отказ на любом шаге не оставляет пароли подменёнными; рестарт прогона
  после сбоя начинается с проверки/восстановления хэшей.

### NFR-004: Usability

- Один флаг включения режима; консольная сводка показывает режим,
  онлайн-статус авторов, факты восстановления.

## Out of Scope

- Животноводство, планирование, arm-fuel-expense для авто-ПЛ (бэклог).
- Веб-клиент как обязательный режим (T7 остаётся Could Have/лицензия).
- Изменение механизма подмены паролей (спека 001 — заморожена, used as-is).
- Изменение прав реальных ролей/пользователей в самой базе.

## Questions

### Q-001: Носитель негативных прав — answered (см. D-001)

**Что выбрать ролью негативного пользователя?** В демо-базе роли без
ПолныхПрав много (взаимодействие с RLS конкретного профиля).
- **Why:** определяет, какие ошибки будут воспроизведены; если роль
  слишком ограничена — негативные сценарии тривиальны; слишком широка —
  могут случайно проходить.
- **Options:**
  - (A) Существующая роль без ПолныхПрав из состава ERP (напр., базовая
    роль «Пользователь» без профиля АПК) — реалистично, минимальный код.
  - (B) Специально созданная роль с явным запретом на объекты АПК-документов —
    детерминированно, но роль надо создавать/удалять.
  - (C) Реальный ограниченный пользователь демо-базы, если есть.
- **Impact:** сложность фикстур, реалистичность, стабильность.
- **Recommended:** (B) — детерминированность важнее реалистичности для
  регресса; роль создаётся/удаётся прогоном как негативный пользователь.

### Q-002: Пустой бак/деградация для негативных пользователей — answered (см. D-002)

Негативный пользователь не пишет документы, но сценарий всё равно строится
на данных (негативный сценарий = попытка проведения ПЛ). Использовать
ли --baseline-dt для каждого прогона (рекомендовано) или пополнять баки
ведомостями?
- **Recommended:** --baseline-dt всегда для режима реальных авторов
  (воспроизводимость), ведомости — только для ручных прогонов.

### Q-003: Smoke под кем? — answered (см. D-003)

В режиме реальных авторов smoke-сценарий (подключение TestClient) остаётся
под одним из авторов или создаётся один зонд?
- **Recommended:** smoke под первым автором манифеста (без зондов вообще);
  если подключение под автором нестабильно — fallback на зонд с пометкой.

## Decisions

### D-001: Негативный пользователь — временная роль + временный пользователь

**Decision:** прогон создаёт временную роль с явным запретом прав на
объекты АПК-документов (вариант B) и временного пользователя с этой
ролью; оба удаляются при завершении (finally-семантика, как зонды).
**Reason:** детерминированность важнее реалистичности для регресса;
не зависим от чужих профилей/RLS существующих ролей.
**Source:** Q-001. **Impacts:** FR-004, FR-005, NFR-002.

### D-002: Воспроизводимость — --baseline-dt по умолчанию для режима авторов

**Decision:** прогоны с реальными авторами выполняются с `--baseline-dt`
(рекомендация по умолчанию в runbook); пополнение баков ведомостями —
только для ручных отладочных прогонов.
**Reason:** режим добавляет батчей → больше деградации базы;
воспроизводимость baseline-сравнения первична.
**Source:** Q-002. **Impacts:** FR-001, FR-007, NFR-001.

### D-003: Smoke под первым автором манифеста

**Decision:** в режиме реальных авторов smoke выполняется под первым
автором из манифеста, без создания зондов; при нестабильности подключения
под автором — fallback на один зонд с пометкой в отчёте.
**Reason:** цель режима — проверка под реальными правами; лишние
пользователи в базе не нужны.
**Source:** Q-003. **Impacts:** FR-001, FR-006.
