## 1. Executive Summary

Режим `--real-authors` в регресс-команде: батчи выполняются под реальными
авторами документов (манифест без restrict-ограничения), **подмена паролей
всегда** (решение пользователя: механизм должен отрабатываться на демо-базе,
т.к. на базах заказчиков у авторов есть пароли), восстановление исходного
состояния per-user при любом исходе. Негативное покрытие: постоянная пустая
роль в новом micro-CFE + временный пользователь `АпкСценТест_Негатив1`,
негативный сценарий — честно красный в VA, вердикт инвертируется на уровне
отчёта по тексту ожидаемой ошибки.

Ключевая корректировка требований фактами: **D-001 в букве «роль создаётся
прогоном» нереализуема** — роль из COM в Предприятии не создаётся
(`facts-com-probes.md` Q-D2 #1). Роль становится постоянным артефактом
micro-CFE (uuid в git), прогон создаёт/удаляет только пользователя.
Смысл D-001 (детерминированность через собственную роль, не чужие профили)
сохранён.

## 3. System Architecture (что меняется)

```text
regress_run.py            +--real-authors, patch_settings_for_real,
                            rac_sessions_online(), BASELINE_REAL, отчёт, guard-check
t8_gate.py                +real-ветка (skip restrict_manifest/Зонды),
                            create_neg_user, add_negative_batch,
                            record_authors_state/verify_real
АпкПодготовкаСценарныхТестов (EPF, ObjectModule.bsl + Module.bsl форм)
                          +ПодменитьПарольБезусловно, ветка ВосстановитьПароль,
                            pwdSubstituted/negative в отчёте
АпкРаннер (t6-зеркало)    +та же ветка подмены (Сервер_ПодменитьПарольБезусловно)
src/cfe/АпкСценТестНегРоль (micro-CFE)     — НОВЫЙ: пустая роль АпкСценТестНегатив
tests/templates/neg-pl-denied.feature      — НОВЫЙ: негативный шаблон
tests/baseline/baseline-real.json          — создаётся --set-baseline
```

Режим доставляется **одним каналом**: `--real-authors` →
`patch_settings_for_real()` (backup + restore в finally, по образцу
`patch_settings_for_web`) → ключи в `preprocessor-settings.json` →
гейт и EPF читают настройки (первая строка лога гейта = режим).

## 4. TD-001: Механизм паролей (FR-002, NFR-002/003)

**Подмена всегда.** Замороженный `ПодменитьПароль` (ObjectModule.bsl ~672) —
байт-в-байт. Новый экспорт **`ПодменитьПарольБезусловно`** (после ~701):
вызывает замороженную функцию (снимок {ПарольУстановлен, Хэш, ЗОД}); если
`НЕ ПарольУстановлен` → `ПользовательИБ.Пароль = ТестовыйПароль; Записать()`;
в снимок добавляет `УстановленТестовый` (для отчёта). ЗОД-логика — как в
замороженной функции, не трогается.

`ПодготовитьПрогон` (~624): чтение настройки `alwaysSubstitutePwd`;
`Батч.ПодменятьПароль = ПользовательИБ.ПарольУстановлен ИЛИ ВсегдаПодменять`.
Существующий `ЗаписатьVAParamsБатча` (~756) уже следует
`Батч.ПодменятьПароль` — клиент подключается с тестовым паролем.

**Восстановление обеих веток.** `ВосстановитьПароль` (~712): НОВАЯ ветка
`ПарольУстановлен = Ложь` → `ПользовательИБ.Пароль = ""; Записать()` +
верификация повторным чтением `Проверка.ПарольУстановлен = Ложь`.
Результат: поле `ПарольВосстановлен` (истина в обеих ветках; `ХэшВосстановлен`
сохраняется для совместимости со старыми сборками EPF).

**Раннер** (target Module.bsl + t6-зеркало, зеркально): ветка по
`Батч.ПодменятьПароль` → сервер-обёртка `Сервер_ПодменитьПарольБезусловно`;
в `Результат` добавляется `pwdSubstituted` (устанавливается после успешной
подмены); существующий per-batch finally as-is. Пересборка обоих EPF.

**Оборона восстановления (3 уровня + guard):**
1. per-batch finally раннера (уже есть);
2. гейт: `record_authors_state` — COM-снимок `ПарольУстановлен` авторов ДО
   Stage B, `verify_real` после — сверка исходного состояния;
3. rollback RestoreIB (наследие 003) как последняя сеть;
4. guard-файл ДО подмены: `tests/pwd-guard/<user-latin>.json`
   {user, passwordInstalled, hash, zod, runId, active} — каталог в
   .gitignore; `active=false` после успешного restore. При старте
   `--real-authors` — guard-check: активные снимки → отказ до прогона +
   инструкция runbook. Идемпотентность обеих веток восстановления.

Отложено (до первого реального инцидента): полный EPF-recover-режим
(`mode=pwdRecover`). COM-установка `СохраняемоеЗначениеПароля` из Python —
НЕ используется (фактами не подтверждена).

## 5. TD-003: Режим манифеста (FR-001, D-002/D-003)

- Флаг `--real-authors`; взаимоисключим с `--web-client` (argparse error,
  exit 2). С `--update` разрешён (предупреждение в лог; runbook рекомендует
  `--baseline-dt`, D-002).
- `patch_settings_for_real`: ключи `realAuthors`, `alwaysSubstitutePwd`,
  `negUser`, `negUserRoles` в `preprocessor-settings.json` (backup →
  restore_settings в finally).
- Гейт (t8_gate.py), real-ветка: НЕ создаёт Зонд1/Зонд2, НЕ вызывает
  `restrict_manifest` — манифест используется как сгенерированный
  (`features-manifest.generated.json` == `features-manifest.json`).
- **Smoke-нормализация** (D-003): в манифесте остаётся первая 00-smoke-запись,
  переназначенная на первого автора манифеста; остальные smoke-записи
  отбрасываются. Зонды не создаются вообще.
- **add_negative_batch**: копия neg-шаблона в features-каталог прогона +
  append в манифест записи строго по формату restrict_manifest:
  `{"file","template","user":<negUser>,"scenarios":1,"documents":[],"negative":true}`.
  Флаг `negative` в манифесте → батч → результат (не хардкод имени!).
- Зондовый путь (без флага) — нулевой дифф.

## 6. TD-002: Негативная роль и пользователь (FR-004/005)

**Носитель роли — НОВЫЙ micro-CFE** `src/cfe/АпкСценТестНегРоль`
(имя без коллизии с EPF «АпкПодготовкаСценарныхТестов»; в EPF роли
встроить нельзя — там нет Configuration.xml). Состав: Configuration.xml +
`Roles/АпкСценТестНегатив/` (uuid фиксируется в git) + пустой
`Ext/Rights.xml` по образцу существующих 5-строчных
(`АпкПропускКонтроляОстатковПоЖивотноводству`). Загрузка — db-load-xml
(однократно, +UpdateDB), затем round-trip verify + db-cfe-admin «проверка
применимости». Префлайт прогона проверяет наличие расширения и ролей (exit 2).

**Блокер-зонд до реализации:** видна/назначаема ли роль CFE из
COM-Предприятия (`u.Роли.Добавить` по метаданным расширения). 2 неудачи →
fallback: роль в основной конфигурации (APKModSrc + db-load-xml).

**Состав ролей neg-пользователя** (права аддитивны, «запреты» в роли не
работают): `negUserRoles = ["БазовыеПраваБСП", "АпкСценТестНегатив"]` —
настраиваемо; default по фактам (никаких «БазовыеПрава»). Аудит XML
`БазовыеПраваБСП` до E2E: отсутствие Insert/Update/Post на `Document.Апк*`
(Read допустим — негатив строится на записи/проведении, не на открытии).

**Пользователь `АпкСценТест_Негатив1`**: временный, создаётся гейтом
(`create_neg_user` по образцу `create_user`: пароль P1-стиля только в
памяти/VAParams, ЗОД off, роли из negUserRoles), удаляется в mode-зависимом
finally (2 попытки + переподключение при отказе). Предопределённые попытки
подключения TestClient под ним — зонд №2 до E2E.

## 7. TD-005: Онлайн-проверка авторов (FR-003)

Новая `rac_sessions_online()` в regress_run.py (~20 строк, cp866-декод по
образцу `rac_jobs_deny_get`; посылка «парсер session list уже есть» — ложная).
Два рубежа:
1. **Preflight** (до do_dump и любых изменений): сессии dev_erpapk_demo;
   allowlist = {Администратор (ОрловАВ)} + сервисные (пустой user-name);
   чужие → перечень в лог → exit 2 (EXIT_INFRA), база и пароли не тронуты.
2. **Гейт после Stage A** (манифест уже известен, до создания neg-пользователя
   и Stage B): повторный rac-вызов, пересечение user-name с авторами
   манифеста → `finish(False)`.

Остаточный TOCTOU (между рубежом 2 и подменой) — принять, задокументировать
в runbook (окно — тихие часы).

## 8. TD-006: Отчёт (FR-006, NFR-004)

- Заголовок: `режим: real-authors (авторы: ...)`.
- Таблица батчей: user (автор), `pwdSubstituted`, `passwordRestored`,
  негатив-флаг (из манифеста).
- Раздел «Авторы и восстановление паролей»:
  `| автор | подменён | восстановлен | верификация |` — только булевы факты.
- Таблица сценариев: колонка «тип» (позитив/негатив) + вердикт негатива;
  totals `negativePassed/negativeFailed`.
- Консольная сводка: режим, онлайн-статус, N/N подменено/восстановлено,
  neg-вердикт, факт удаления neg-пользователя.

## 9. TD-004: Baseline режима (FR-007)

- `BASELINE_REAL = tests/baseline/baseline-real.json`; `read_baseline()/
  write_baseline()` параметризуются путём; `diff_classes` as-is (ключ
  (scenario, user) общий; негативный user-ключ стабилен фиксированным
  именем temp-пользователя).
- **Зелёность режима**: позитивы passed == scenarios_positive И
  `negativePassed == scenarios_negative` И все батчи `passwordRestored`.
- Diff негативных строк — по effective-status (verdict): REGRESSION по
  негативу = «негатив перестал воспроизводиться».

## 10. Вердикт негативного сценария (FR-005)

- Носитель: `tests/templates/neg-pl-denied.feature` — навигация → создание →
  **запись/проведение** ПЛ (шаги из живых фич 01/02-*; НЕ «открытие формы» —
  Read у БазовыеПраваБСП может быть разрешён). Сценарий честно красный в VA,
  шаги-перехватчики окна ошибки НЕ выдумываются.
- Инверсия в `СобратьОтчет` (ObjectModule.bsl): `status=failed` И
  `statusDetails.message` матчит константу **ПАТТЕРНОТКАЗА**
  (`Недостаточно прав|Нет прав` — точный текст фиксирует зонд №2) →
  **neg-pass**; `passed` → neg-fail «неожиданно прошло»; `failed` без
  матчинга → neg-fail «чужая ошибка» (+ хвост message в отчёт); батч умер до
  allure → neg-fail «среда». Любое расхождение = FAIL.
- Гейт `verify_real`: neg-батч `rs != 0` И все его сценарии neg-pass.
- Ретрай stage-b: rs=1 neg-батча НЕ триггерит retry (retry — только rs=2;
  проверить факт при реализации).

## 11. TD-007: Лицензии и веб (FR-009)

Кодовых изменений нет. Runbook: тонкие TestClient параллельно — неограниченно
(аппаратный ключ); веб-клиент — эксклюзивный отдельный прогон (комбинировать
нельзя); лицензионный отказ в вебе при живых тонких сессиях = вердикт
«среда». FR-009 остаётся Could Have.

## 13. Edge Cases

| Case | Expected Behavior |
|------|-------------------|
| У автора появился пароль между запусками | Подмена/восстановление работают по ветке ПарольУстановлен=True (замороженный механизм) |
| Прогон убит посреди Stage B | guard-файл active=true; guard-check при следующем старте → отказ + runbook-протокол; rollback RestoreIB доступен |
| Автор зашёл в базу после рубежа 2 (TOCTOU) | Возможен конфликт сеансов; задокументирован, окно — тихие часы; runbook |

## 16. Implementation FAQ

**Q: Почему не третий параметр у замороженного ПодменитьПароль?**
A: заморозка спеки 001 = байт-в-байт; новый экспорт вызывает замороженную
функцию и лишь дополняет поведение. Обратная совместимость старых EPF —
fallback на ХэшВосстановлен.

**Q: Что если автор без пароля, а мы обязаны «подменять всегда»?**
A: ПодменитьПарольБезусловно ставит тестовый пароль даже при
ПарольУстановлен=False; восстановление чистит пароль (`Пароль=""`) и
верифицирует ПарольУстановлен=False (факт Q-D1 #6).

**Q: Почему вердикт негатива не в VA-шагах?**
A: шаги-перехватчики окна ошибки капризны и дают ложный PASS на чужой
ошибке (нарушение FR-005). Надёжнее инверсия на уровне СобратьОтчет по
statusDetails.message из allure-результата, который уже читается.

**Q: Негатив в общем baseline.json?**
A: нет — сравнение режимов бессмысленно; отдельный baseline-real.json,
зелёность режима включает negativePassed и passwordRestored всех батчей.
