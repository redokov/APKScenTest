## Overview

Финальная фаза roadmap v1: превратить работающий конвейер APKScenTest
(скан → фикстуры → фичи → батчи → отчёт) в **one-command регресс-прогон**
для процедуры «обновили релиз ERP+АПК на тестовой базе → прогнали регресс →
получили отчёт». Администратор выполняет одну команду с одним входным
параметром (путь к «обновлению»), после чего получает отчёт: какие
бизнес-сценарии растениеводства работают, какие сломались, и что
регрессировало относительно эталонного (baseline) прогона.

Кто это для: администратор/инженер АПК, обслуживающий тестовую базу
`dev_erpapk_demo` и получающий релизы ERP+АПК.

Почему важно: конвейер и покрытие доказаны (спеки 001–002), но процедура
регресса после обновления релиза пока не упакована — нет одной команды,
нет безопасного цикла «дамп → обновление → прогон → откат», нет
baseline-сравнения и нет инструкции для администратора.

## Business Context

- **Problem:** обновление релиза на демо-базе — ручная процедура;
  последствия обновления для сценариев растениеводства неизвестны без
  ручного прогона; эталон для сравнения («что работало до обновления»)
  не зафиксирован как артефакт.
- **Users:** администратор демо-базы (запускает команду), инженер АПК
  (читает отчёт, решает «релиз сломал регрессию или нет»).
- **Value:** решение «принять/отклонить релиз» по одному отчёту;
  воспроизводимость процедуры любым администратором по runbook.
- **Success signal:** после «обновления» одна команда даёт отчёт со
  статусами 5/5 сценариев и пометками регрессии против baseline;
  демо-база после процедуры возвращается в исходное состояние (dt-откат).

## Goals

- One-command прогон регресса на `dev_erpapk_demo` с гарантированным
  dt-дампом до и откатом после (демо-база — общая, данные пользователей
  сохраняются).
- Отчёт регресса: сценарий × пользователь × статус × регрессия против
  baseline, на базе существующих артефактов прогона (run-каталог,
  allure-результаты VA, сводка).
- Реестр baseline-запусков: последний зелёный прогон фиксируется как
  эталон, с которым сравниваются последующие.
- `docs/runbook.md`: пошаговая инструкция администратора (включая
  вариант через веб-клиент, D7).

## Non-Goals / Out of Scope

- Автоматическое применение реальных релизных обновлений из внешних
  источников (загрузчики релизов, EDT/gitsync) — конвейер принимает
  уже подготовленный артефакт «обновления» (dt/CF/XML) по пути.
- Реальные пользователи-авторы в прогонах — пока только временные зонды
  (наследие D-001 спеки 002; включение реальных авторов — отдельное
  явное разрешение пользователя).
- Новые сценарии/шаблоны покрытия (включение arm-fuel-expense в батч
  авто-ПЛ 02-pl-auto, животноводство, негативные сценарии) — вне скоупа.
- Allure-commandline и HTML-отчёты — не ставим (D3).
- CI/CD-интеграция (запуск по расписанию/GitHub Actions) — не сейчас.

## User Stories

### US-001: One-command регресс после обновления

**As a** администратор демо-базы
**I want to** выполнить одну команду с одним параметром (путь к
«обновлению») и получить готовый отчёт регресса
**So that** процедура проверки релиза занимает минуты и не требует знания
внутреннего устройства конвейера

**Acceptance Criteria:**
- [ ] Команда дампит базу (dt), применяет «обновление», прогоняет E2E-гейт,
  откатывает базу из dt и формирует отчёт — без ручных промежуточных шагов
- [ ] Любой сбой на промежуточном шаге оставляет базу в исходном состоянии
  (откат из dt выполняется гарантированно)
- [ ] Итог: run-каталог с артефактами + сводка сценариев (статусы)

### US-002: Отчёт регресса с baseline-сравнением

**As a** инженер АПК
**I want to** видеть в отчёте по каждому сценарию: статус, пользователя
(зонд), и сравнение с baseline-прогоном (pass→fail = регрессия)
**So that** решение «релиз что-то сломал» принимается по данным, а не по
ощущениям

**Acceptance Criteria:**
- [ ] Отчёт содержит таблицу сценарий × пользователь × статус ×
  «против baseline» (PASS/FAIL/REGRESSION/NEW)
- [ ] Регрессия (pass→fail против baseline) подсвечена явно
- [ ] Отчёт читается без запуска VA (файл в run-каталоге + краткая сводка
  в консоль по завершении команды)

### US-003: Реестр baseline-запусков

**As a** инженер АПК
**I want to** чтобы последний зелёный прогон фиксировался как baseline, и
новые прогоны сравнивались с ним
**So that** сравнение всегда актуально и не требует ручного выбора эталона

**Acceptance Criteria:**
- [ ] Успешный прогон может быть зафиксирован как baseline (команда/флаг)
- [ ] Реестр хранит метаданные baseline (runId, дата, состав сценариев,
  статусы) и путь к артефактам
- [ ] Прогон сравнивается с последним зафиксированным baseline; при его
  отсутствии сравнение пропускается с явной пометкой в отчёте

### US-004: Runbook администратора

**As a** администратор демо-базы
**I want to** пошаговую инструкцию: как подготовить артефакт «обновления»,
запустить регресс, прочитать отчёт и откатить базу при проблемах
**So that** процедуру может выполнить человек, не писавший конвейер

**Acceptance Criteria:**
- [ ] `docs/runbook.md`: подготовка, запуск, чтение отчёта, действия при
  сбоях, ручной откат
- [ ] Runbook протестирован на репетиции «дамп → псевдо-обновление →
  прогон → откат → прогон»
- [ ] Указаны ограничения (зонды, демо-данные, время прогона)

### US-005: Веб-клиент в прогоне (D7) — Should

**As a** инженер АПК
**I want to** чтобы сценарии могли выполняться не только тонким клиентом,
но и веб-клиентом (ТипКлиента из VAParams)
**So that** регресс проверяет и веб-интерфейс публикации базы

**Acceptance Criteria:**
- [ ] Веб-публикация `dev_erpapk_demo` через Apache работает (скил
  web-publish)
- [ ] Прогон с ТипКлиента=web завершается с явным вердиктом (или
  отложен с фиксацией причины в design.md)

## Functional Requirements

### FR-001: One-command регресс-прогон — Must Have

WHEN администратор выполняет команду регресса в режиме `--rehearsal`
(репетиция, без обновления) или `--update <path>` (применение обновления)
IF база доступна и артефакт обновления существует
THE SYSTEM SHALL выполнить последовательность: dt-дамп → применение
обновления (для `--update`) → E2E-прогон (существующий гейт) → dt-откат →
сбор отчёта
SO THAT процедура регресса воспроизводима одной командой

### FR-002: Гарантированный откат демо-базы — Must Have

WHEN команда регресса завершилась (успех, ошибка или прерывание)
THE SYSTEM SHALL восстановить демо-базу из dt-дампа, сделанного до
обновления, и подтвердить откат проверкой
SO THAT данные демо-базы не теряются ни при каком исходе прогона

### FR-003: Отчёт регресса (сценарий × пользователь × статус) — Must Have

WHEN E2E-прогон завершён
THE SYSTEM SHALL сформировать отчёт по каждому сценарию: статус
(PASS/FAIL), пользователь-зонд, батч, длительность
SO THAT инженер видит результат прогона без разбора логов VA

### FR-004: Сравнение с baseline — Must Have

WHEN в реестре есть зафиксированный baseline
THE SYSTEM SHALL сравнить статусы сценариев текущего прогона с baseline
и пометить регрессии (pass→fail), новые и исчезнувшие сценарии
SO THAT обновление релиза оценивается именно как «что сломалось»

### FR-005: Реестр baseline-запусков — Should Have

THE SYSTEM SHALL хранить реестр baseline-прогонов (runId, дата, состав,
статусы, путь к артефактам) и позволять зафиксировать последний
успешный прогон как новый baseline

### FR-006: Runbook — Should Have

THE SYSTEM SHALL поставлять `docs/runbook.md` с процедурой регресса,
включая действия при сбоях и ручной откат

### FR-007: Веб-клиент в прогоне — Could Have

THE SYSTEM SHALL уметь прогонять сценарии веб-клиентом (ТипКлиента из
VAParams), при включённой веб-публикации базы
SO THAT покрытие включает веб-интерфейс (D7); при отсутствии публикации —
отложено с фиксацией в design.md

### FR-008: Ретро релиза 2 — Could Have

THE SYSTEM SHALL (процессуально) зафиксировать в PLAN.md решения ретро
релиза 2 (животноводство / планирование / прочее) по итогам релиза 1

## Non-Functional Requirements

### NFR-001: Performance

- Полный регресс-прогон (5 сценариев, 2 батча, 2 зонда) ≤ 40 мин
  (фактическая база: 12.7–18.3 мин без стадии дампа/обновления).

### NFR-002: Security / данные

- Прогоны — только под временными зондами (D-001 спеки 002);
  реальные пользователи не затрагиваются, хэши паролей восстанавливаются
  (механизм спеки 001).
- «Обновление» применяется только к копии процедуры на демо-базе с
  обязательным dt-откатом; реальные данные 2015–2023 не трогаются.

### NFR-003: Reliability

- Вердикты — по ReturnStatus-файлам VA (проверенный паттерн), таймауты
  на каждый прогон, kill-tree при зависании.
- Отказ любого шага конвейера не оставляет базу в промежуточном
  состоянии (NFR/FR-002).

### NFR-004: Usability

- Одна команда, один обязательный параметр; все артефакты прогона — в
  одном run-каталоге; итоговая сводка печатается в консоль.

## User Experience Notes

- Основной поток: подготовить артефакт обновления → запустить команду →
  дождаться сводки в консоль → открыть отчёт в run-каталоге.
- Пустое состояние: baseline не зафиксирован → отчёт без колонки
  сравнения, с пометкой «нет baseline».
- Ошибка обновления/прогона: команда завершается ненулевым кодом,
  база откачена, в сводке — причина сбоя и путь к логам.

## Constraints

- Запуск VA — только тонким клиентом `1cv8c` (без веб-командной строки
  для запуска VA). Веб-клиент (FR-007) — только как ТипКлиента VA при
  опубликованной базе.
- Демо-база `dev_erpapk_demo` общая: откат через dt-дамп обязателен на
  каждый прогон с «обновлением».
- Известные девиации покрытия (наследие спеки 002, действуют и здесь):
  авто-ПЛ 02-pl-auto не закрывается (пустой АпкСкладБака у КАМАЗ-65115,
  real data) — авто-запись РасходаТоплива `when: never` до подбора ТС;
  период arm-шаблонов статичен (01–31.10.2026) — при смене месяца фикстуры
  актуализируются руками.
- Веб-публикация Apache требует интерактивной сессии (GUI/headsless —
  уточняется перед T4).
- Инструментарий регресса наследует rollback-скрипты спек 001–002
  (`s2_rollback_*`, `t9_rollback_*`) как часть арсенала.

## Decisions

### D-001: Прогоны под временными зондами (унаследовано из спеки 002)

**Decision:** все батчи регресса выполняются под временными зондами;
реальные авторы — только после явного разрешения пользователя.
**Reason:** безопасность реальных пользователей демо-базы.
**Source:** D-001 спеки 002 (подтверждено пользователем)
**Impacts:** US-001, US-002, NFR-002, FR-003

### D-002: Веб-клиент — Фаза 4, по флагу (наследие D7 roadmap)

**Decision:** веб-клиент включается в регресс опционально, после
веб-публикации базы; тонкий клиент остаётся основным.
**Reason:** D7 roadmap; публикация через Apache — отдельная зависимость.
**Source:** PLAN.md D7
**Impacts:** FR-007, US-005

### D-003: Allure — каталог результатов VA + собственная сводка (D3)

**Decision:** allure-commandline не ставим; отчёт регресса строится из
allure-результатов VA и собственных артефактов.
**Reason:** D3 roadmap.
**Source:** PLAN.md D3
**Impacts:** FR-003, FR-004

### D-004: CLI-контракт — единый Python-раннер

**Decision:** `python scripts/regress_run.py [--rehearsal | --update <path>]`,
обёртка над существующим гейтом; без дополнительного фасада.
**Reason:** один вход, консистентность со скриптовым арсеналом `scripts/`.
**Source:** Q-001
**Impacts:** FR-001, US-001, NFR-004

### D-005: Baseline — JSON-сводка статусов в git

**Decision:** baseline = JSON-сводка (runId, дата, состав сценариев,
статусы) в `tests/baseline/` под git; полные артефакты — по ссылке на
локальный run-каталог (вне git).
**Reason:** переносимый эталон при минимальном весе репо.
**Source:** Q-002
**Impacts:** FR-004, FR-005, US-003

### D-006: Веб-клиент — опциональный флаг, отложенный при headless

**Decision:** FR-007 реализуется флагом; если сессия headless или
публикация не поднята — откладывается с фиксацией в design.md.
**Reason:** минимизация риска при сохранении D7; критерий готовности
спеки допускает откладывание.
**Source:** Q-003
**Impacts:** FR-007, US-005

### D-007: Вход «обновления» — два режима: rehearsal и update

**Decision:** поддержать `--rehearsal` (дамп → прогон → откат, без
обновления) и `--update <path>` (CF или dt-файл по пути).
**Reason:** сначала доказать безопасность процедуры, затем реальный
контракт.
**Source:** Q-004
**Impacts:** FR-001, US-001, Risks

### D-008: Ретро релиза 2 — короткой задачей в конце спеки

**Decision:** ретро (FR-008) — отдельная задача в конце спеки:
обсуждение с пользователем + правка PLAN.md.
**Reason:** естественный финал Фазы 4; без кода.
**Source:** Q-005
**Impacts:** FR-008

## Glossary

- **Регресс-прогон:** полный E2E-прогон конвейера (генерация фич из
  фикстур → батчи под зондами → вердикты) в обёртке
  «дамп → обновление → прогон → откат → отчёт».
- **Baseline:** зафиксированный эталонный прогон (статусы сценариев),
  с которым сравниваются последующие прогоны.
- **Зонд:** временный пользователь с тестовым паролем, создаваемый
  препроцессингом на прогон и удаляемый после (D-001).
- **Rehearsal-режим:** репетиция регресса без реального обновления
  (дамп → прогон → откат), доказывающая безопасность процедуры.
