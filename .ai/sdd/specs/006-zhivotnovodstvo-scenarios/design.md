# Design: Животноводство — сценарии группового учёта СВН и КРС (спека 006)

> Requirements: @requirements.md
> Status: **Draft** (ждёт утверждения пользователя)

## 1. Summary

Расширяем принятый E2E-конвейер (спеки 001–005) на животноводство
**данными, а не кодом**: coverage-map уже управляет сканом/фикстурами/
генерацией, авторы и батчи строятся автоматически из скана, neg/baseline/
отчёт — общие механики. Основная работа — 14 Must-шаблонов `.feature`
(6 СВН + 8 КРС) по playbook'у probe-first (спека 002), записи в
`tests/coverage-map.json`, neg-шаблон животноводства, расширение
baseline и инструкции. Правки BSL — только там, где probe покажет
новые типы полей/форм подбора, которых экстрактор не умеет.

## 3. Technical Approach

### 3.0. Порядок реализации — probe-first (playbook спеки 002)

Каждый шаблон = probe-фича под админом (без подмены пароля, без записи
данных; созданный в probe документ удаляется) → стабилизация шаблона →
включение в манифест полного цикла. Полный объединённый прогон
(растениеводство + животноводство) — только после стабилизации всех
Must-шаблонов. При UIA-флейке — правило idle-десктопа (ретро Фазы 6).

### 3.1. Скан и генерация: расширение coverage-map.json (TD-001)

`tests/coverage-map.json` → `documents` получает новые записи
(ключ = имя типа документа, значение = {template, fieldList, valueMaps,
axes}):

**СВН (Must, 6):** АпкГрупповойОпорос (10-svn-farrowing),
АпкГрупповоеВзвешиваниеЖивотных (11-svn-weighing),
АпкГрупповойПадежЗабой (12-svn-mortality),
АпкГрупповоеПоступлениеЖивотных (13-svn-receipt),
АпкГрупповоеПеремещениеЖивотных (14-svn-movement),
АпкГрупповойУчетныйЛистДвиженияЖивотных (15-svn-accounting-sheet).

**КРС + молоко (Must, 8):** АпкЖурналНадояМолока (16-krs-milk-journal),
АпкКРСГрупповойУчетныйЛистДвиженияЖивотных (17-krs-accounting-sheet),
АпкКРСГрупповоеПоступлениеЖивотных (18-krs-receipt),
АпкКРСГрупповойПеревод (19-krs-transfer),
АпкКРСГрупповоеВзвешиваниеЖивотных (20-krs-weighing),
АпкКРСГрупповойОтел (21-krs-calving),
АпкКРСТТНМолоко (22-krs-milk-ttn),
АпкВнутреннийРасходМолока (23-krs-milk-internal).

`fieldList`/`valueMaps`/`axes` для каждой записи определяются на probe-
этапе по Form.xml/метаданным (как в 002): шапка (Организация,
Свинокомплекс/Ферма, Корпус/Секция, группа животных/партия, статусы,
ответственные) + ТЧ (строки животных/групп, надой, расходы и пр.).
Should-типы (ещё 22, D-003) добавляются аналогичными записями по мере
стабилизации их шаблонов — правка данных, без кода.

Поток генерации не меняется: те же фикстуры → те же шаблоны → тот же
run-каталог (FR-002). Пробы фиксируют, читаются ли новые типы полей
(ссылки на АпкФермы/АпкКорпуса/АпкПартии, перечисления видов операций)
штатным экстрактором; если нет — точечная правка экстрактора (единственная
возможная правка BSL, см. §9 FAQ).

### 3.2. Шаблоны .feature (TD-002)

15 новых файлов в `tests/templates/` (14 Must + 1 neg, имена —
`10-svn-farrowing.feature` … `23-krs-milk-internal.feature`,
`neg-livestock-denied.feature`). Структура шагов — по образцу
01-pl-tractor (probe-first грабли 8.5.4 в docs/next-session-prompt.md):
открытие формы документа → заполнение шапки по фикстуре → ТЧ →
запись/проведение → закрытие. Сценарии работают на введённых документах
(представитель), не создают данные с нуля.

### 3.3. Батчи авторов: ФедоровБМ добавляется автоматически (TD-003)

Скан собирает пользователей-авторов и строит батчи; источник — авторы
документов + привязка справочника Пользователи → ИБ-пользователь
(`ИдентификаторПользователяИБ`). Разведка подтвердила: Федоров Борис
Михайлович есть в справочнике, ИБ-пользователь
`Администратор (ФедоровБМ)` существует. Ожидаемые батчи после расширения:
ОрловАВ (растениеводство + СВН 100% + часть КРС), СоколовМИ
(растениеводство), ФедоровБМ (КРС/молоко), neg. Подмена/восстановление
хэшей — действующий механизм, +1 пользователь (NFR-003): тот же цикл
substitute→run→restore, гарантия восстановления во всех ветках, отчёт
mismatch=[].

### 3.4. Neg-механика: генерируемый пользователь, новый neg-шаблон (TD-004)

Neg-пользователь — тот же генерируемый `АпкСценТест_Негатив1` (рецепт
T5: 5 ролей, без прав животноводства). Neg-шаблон
`neg-livestock-denied.feature`: попытка записи документа животноводства
(групповой опорос — самый наполненный тип) без прав → ожидаемая ошибка
→ neg-passed. Инверсия вердикта, restrict-manifest, паритет MISSING в
частичном плане — действующие механики раннера (спека 004/T5), без
правок.

### 3.5. Baseline: единое действие фиксации (TD-005)

Новые сценарии попадают в сравнение как NEW до первой фиксации эталона.
После зелёного объединённого прогона — то же действие раннера
«зафиксировать эталон» (доступно только при зелёном): baseline.json
расширяется ключами (сценарий|пользователь) животноводства. Отдельной
фазы/файла для животноводства не заводим — единый baseline комплекта
(FR-006).

### 3.6. Сводный по реализации молока (D-005 requirements)

Оба документа АпкКРССводныйДокументПоРеализацииМолока в базе не
проведены. На probe-этапе — разведка причин (журнал регистрации,
попытка интерактивной записи под админом): если исходник патологический
— шаблон не пишем, сценарий остаётся Should-skip с причиной (FR-003);
если рабочая механика — шаблон в Should-волну.

## 4. Комплект и инструкция (FR-007/FR-008)

dist/scenarios/ расширяется только файлами: новые шаблоны `.feature`,
(если появятся) патчи `scenario-patches.json`, обновлённый
`baseline.json`. Состав комплекта неизменен: 3 EPF + сценарии +
ИНСТРУКЦИЯ.md. В ИНСТРУКЦИЮ добавляется раздел «Животноводство»: какие
документы/справочники-каркас должны быть в базе, третий пользователь-
автор (ФедоровБМ), ожидаемое время прогона.

## 5. Data Model / State

Новых регистров/справочников нет. Фикстуры животноводства — расширение
существующей модели (элементы заполнения из документов): новые ссылочные
типы (АпкСвинокомплексы, АпкФермы, АпкКорпуса, АпкСекции, АпкПартии,
АпкСтатусы*) и перечисления (виды операций). Всё — данные
coverage-map/фикстур, не структура комплекта.

## 6. API / Integration Contract

Не применимо: интеграционных границ нет; внутренние контракты
(coverage-map формат, шаблоны, baseline-ключи, VAParams) — расширение
существующих форматов без breaking-изменений (старые записи читаются
как есть).

## 7. Security / Permissions

Без изменений модели: препроцессор/раннер — только администратор;
хэши паролей — только язык 1С, восстановление во всех ветках; neg-
пользователь генерируется и удаляется существующим рецептом. Права
животноводческих ролей не выдаём никому, кроме авторов (через их
собственные профили) — регресс проверяет именно их RLS.

## 8. Edge Cases

| Case | Expected Behavior |
|---|---|
| Тип документа пуст в базе | skip сценария с причиной в итогах подготовки (FR-003; механика существует — проверить на probe) |
| У автора нет привязки к ИБ-пользователю | сценарий в батч-план не попадает, причина в итогах (как в растениеводстве) |
| Сводный-молоко не проводится | §3.6: skip с причиной либо Should-шаблон |
| Формы подбора животных (АпкПодборЖивотных*) | UIA-ловушки уровня АпкФормаВыбора (002): обрабатывать в шаблоне probe-first, не кодом |
| UIA-флейк interaction-шагов | правило idle-десктопа + 2 зонда/2 разных шага = среда, стоп (ретро Фазы 6) |

## 9. Implementation FAQ

**Q: Как добавить Should-тип документа после спеки?**
A: запись в coverage-map.json + шаблон в tests/templates + патчи при
необходимости; пересборка EPF не нужна (данные).

**Q: Когда всё же правится BSL?**
A: только если probe покажет, что экстрактор не читает новый тип поля
(например, особая форма подбора в шапке). Правка — точечная в
`src/АпкПодготовкаСценарныхТестов/Ext/ObjectModule.bsl`, гейт:
bsl-ls 0 ошибок → сборка → probe.

**Q: Как верифицировать генерацию до живого прогона?**
A: офлайн-гейт — генерация на фикстурах dev_erpapk_demo, дифф
сгенерированных фич по шаблону против эталона (как byte-diff гейт T2).

**Q: Что с dev-time python?**
A: только probes/запуски VA (рецепты s005), в комплект не входят;
новых python-механик в рабочий цикл не добавляем.

## 10. Technical Decisions (сводка)

- **TD-001:** расширение coverage-map.json данными животноводства
  (14 Must-записей), поток скана/генерации без правок.
  *Trade-off:* fieldList/оси определяются эмпирически на probe (не все
  сразу); *альтернатива:* захардкодить список типов в коде — отвергнута
  (нарушает переносимость и модель 001).
- **TD-002:** 15 шаблонов .feature probe-first, имена 10-svn-* …
  23-krs-*, neg-livestock-denied.
- **TD-003:** ФедоровБМ входит в батч-план через существующую механику
  авторов; никаких спец-обработок пользователей.
- **TD-004:** neg = генерируемый АпкСценТест_Негатив1 + neg-шаблон
  животноводства (опорос); механики 004/T5 без правок.
- **TD-005:** единый baseline комплекта, расширение штатным действием
  фиксации после зелёного прогона.
- **TD-006 (D-005 requirements):** сводный-молоко — разведка на probe,
  исход: Should-шаблон либо skip с причиной.

## 11. Verification Strategy

1. Офлайн-гейты: bsl-ls (если правится BSL) 0 ошибок; byte-diff генерации
   против эталона; pre-load валидация не требуется (код EPF не трогаем,
   кроме случая §9).
2. Probe-гейты: каждый шаблон стабильно проходит под админом отдельно
   (критерий: 2 зелёных probe подряд, как в 002).
3. Neg-гейт: neg-only план — neg-passed=1, паритет MISSING = полному
   плану (рецепт t5-negrun).
4. Объединённый полный прогон (idle-десктоп): вердикт PASS, все
   сценарии (растениеводство 17 + животноводство 15+) зелёные, NEW для
   новых, регрессий 0 vs baseline, mismatch=[] пароли.
5. Фиксация эталона → повторный прогон: регрессий 0, все ключи известны.
6. Время: контроль NFR-002 (≤60 мин) на объединённом прогоне
   (ориентир: 17 сценариев ~13 мин; +15 сценариев, батч ФедоровБМ
   добавляет ~2-4 мин оверхеда на подмену/сеанс).

## 12. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Формы подбора животных/спец-формы в шапках — UIA-ловушки | Medium | probe-first, грабли в шаблон, не в код |
| Экстрактор не читает новый тип поля | Low/Medium | точечная правка + гейты §11.1 |
| Данные «тонкие» у части Must-типов (учётный лист 6/12) | Low | представитель всегда есть (36/36 непустых); N=3 строк ТЧ может быть меньше — фиксируем в шаблоне |
| Время объединённого прогона >60 мин | Low | батчинг по авторам уже группирует; arm-сценариев у животноводства нет |
| Сводный-молоко патологический | Low | §3.6, skip с причиной не блокирует |

## 13. Migration / Rollback

Не применимо: миграций нет. Откат = удалить записи животноводства из
coverage-map/шаблоны из манифеста — конвейер растениеводства не
зависит от новых записей (старые ключи не меняются).
