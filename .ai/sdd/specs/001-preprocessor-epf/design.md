# Design: 001 — Обработка `АпкПодготовкаСценарныхТестов`

> Requirements: @requirements.md
> Status: Approved (делегировано пользователем 2026-10-11: «продолжай дальше самостоятельно»)
> Last Updated: 2026-10-11

## 1. Executive Summary

EPF (`src/`, сборка epf-build): управляемая форма + серверный модуль объекта.
Пайплайн из семи блоков (сканер → селектор представителей → сопоставление
пользователей → экстрактор фикстур → генератор feature → менеджер паролей +
раннер VA → репортёр), управляемый из одной формы. Все данные прогона живут
в run-каталоге вне ИБ (fixtures.json, сгенерированные .feature, VAParams,
allure, логи, summary). База не модифицируется. Запуск VA — 1cv8c из кода
обработки (WScript.Shell + taskkill для kill-tree), вердикт — только
ReturnStatus-файл. Карта покрытия «документ → оси → АРМ» — поставляемый
JSON-файл в репо, не метаданные (переносимость, D-014).

## 3. Данные решения

### 3.1 Состав артефактов репозитория

```text
src/АпкПодготовкаСценарныхТестов/          # XML-исходники EPF (epf-build)
tests/templates/NN-<slug>.feature           # шаблоны сценариев (плейсхолдеры)
tests/coverage-map.json                     # карта покрытия (оси + АРМы) — версионируется
tests/preprocessor-settings.json            # умолчания настроек (пути, база, таймауты)
tests/run-<runId>/                          # run-каталог прогона (gitignore)
  fixtures.json                             # фикс. данные + план покрытия
  features/                                 # сгенерированные .feature
  params/vaparams-<user>.json               # временные (удаляются после прогона)
  allure/<user>/*-result.json              # allure-выгрузка VA
  logs/va-<user>.log, preprocessing.log     # логи
  summary.json, summary.md                  # сводка
```

задачах); условия `when` в coverage-map — по явным ветвлениям
`ЗНАЧЕНИЕ(Перечисление.АпкТипыЗатрат...)` в АпкАРМПоОтражениюРасходаТоплива.

## 4. Implementation Design

### 4.0 Структура EPF

```text
АпкПодготовкаСценарныхТестов (ExternalDataProcessor)
  ObjectModule.bsl        # серверный пайплайн: блоки 1–7, экспортные функции
  Form/Форма (УФ)         # форма: фильтры, результат, план, прогресс, отчёт
  Form/Форма/Module.bsl   # клиентские обработчики команд, неблокирующий запуск
```

Блоки — экспортные функции модуля объекта (`Сканировать()`,
`ОтобратьПредставителей()`, `СопоставитьПользователей()`, `СформироватьФикстуры()`,
`СгенерироватьФичи()`, `ВыполнитьПрогон()`, `СобратьОтчет()`); состояние
передаётся структурой `КонтекстПрогона` (не глобальное), сериализуется в
run-каталог (возобновляемость между командами формы).

### 4.1 Сканер + селектор (FR-001, FR-016)

1. Запрос объединением по 5 типам документов (проведённые; реквизиты
   `Проведен`, автор, организация; фильтры — только если заданы в форме).
2. Селектор: группировка найденных по комбинации значений осей из
   coverage-map (`axes`); из каждой группы — первый документ
   (детерминизм: упорядочение по `МоментВремени`); пустые группы
   (значение оси есть в карте, документа нет) → `coverageGaps`.
3. Результат — ТЧ формы «Документы-представители»: тип, номер, автор,
   значения осей, покрываемые АРМы (из `arms` с учётом `when`-условий по
   значениям осей документа).

### 4.2 Сопоставление пользователей (FR-003)

`Документ.Автор` (Справочник.Пользователи) → реквизит
`ИдентификаторПользователяИБ` → `ПользователиИнформационнойБазы.НайтиПоИдентификатору()`
→ `ПользовательИБ.Имя` (+ флаги: `ПарольУстановлен` — из
`СвойстваПользователяИБ`; заблокирован ли). Несопоставленные/заблокированные
→ исключение из плана, предупреждение в форме и отчёте.
(Источник: ERPsrc `ПользователиСлужебный`, `Пользователи`; платформенный API.)

### 4.3 План покрытия и подтверждение (FR-004, FR-011)

План = декартово «пользователь × его документы-представители × сценарии
(ввод/проведение по шаблону типа документа + АРМ-шаблоны из coverage-map)».
ТЧ формы: пользователь, сценарий, документ(-ы), АРМ, причина включения.
Галочками исключаются шаблоны (FR-011). Команда «Запустить прогон
(подменяет пароли)» требует подтверждения (деструктивная фаза).

### 4.4 Экстрактор фикстур (FR-002)

По каждому представителю: шапка + до 3 строк каждой ТЧ (D-004), состав
полей — `fieldList` из coverage-map (согласован с шаблонами). Ссылки —
представления (имена) + UUID; даты документов **не** копируются в данные
сценария — сценарий вводит документ **текущим месяцем** (D-005). Запись
`fixtures.json` — `СериализаторXDTO`/`ЗаписьJSON` (UTF-8).

### 4.5 Генератор feature (FR-005)

Шаблоны `tests/templates/*.feature` с плейсхолдерами `{{путь.в.фикстуре}}`.
Подстановка — простая посимвольная замена в коде 1С (без внешних движков);
имена форм — синонимы из метаданных (`Метаданные.Документы.<Имя>.Синоним`).
Один .feature на (пользователь × шаблон) — сценарии по всем
представителям, покрываемым шаблоном; внутри файла сценарии идут подряд.
Файлы — `run-<id>/features/<NN-slug>--<user>.feature` (латиница, D-002).

### 4.6 Менеджер паролей (FR-006, NFR-002)

На пользователя с паролем, по порядку батча:
1) сохранить `СохраняемоеЗначениеПароля` + `ТипАлгоритмаХешированияПароля`;
2) установить тестовый пароль (случайная строка на прогон, только в памяти);
3) после батча — восстановить хэш. Восстановление — в `Попытка…Исключение…
КонецПопытки` обёртке всего батча (finally-семантика), независимо от
вердикта; при таймауте/kill — восстановление выполняет следующий шаг
раннера (обработка живёт в отдельном сеансе админа, не в убитом процессе).
4) Верификация: сравнение сохранённого и восстановленного хэша — строка в
сводке («пароли восстановлены: ok/mismatch»).
Пользователи без пароля — без подмены (D-007). `ДатаУстановкиПароля` не
восстанавливается автоматически — зафиксировать в FAQ (спайк).

### 4.7 Раннер VA (FR-007, FR-009, FR-010, NFR-003)

Батч = пользователь (D-008): один запуск 1cv8c, TestManager — админ,
TestClient — `/N <пользователь> /P <тестовый>`, порт — уникальный на батч.
VAParams per батч: путь к фиче(-ям) батча, `ВыгружатьСтатусВыполненияСценариевВФайл`
+ путь, `ДелатьОтчетВФорматеАллюр=Истина`, `КаталогВыгрузкиAllureБазовый=<run>/allure`,
`ИмяТекущейСборки=<user>` (подкаталог на батч), `ДобавлятьКИмениСценарияУсловияВыгрузки`
(метки пользователь/сборка), отключение ЗОД-предупреждений (имя параметра
уточнить по JsonParamsRU.md; спайк отключал их настройкой).

Запуск процесса: `WScript.Shell` → `Exec("cmd /c <1cv8c ...>")`, PID
оболочки; ожидание статуса с таймаутом (настраиваемый, умолчание 10 мин/
батч); таймаут → `taskkill /PID <pid> /T /F` (kill-tree), статус батча
«timeout», пароль восстанавливается, план продолжается (FR-009).
Вердикт батча — только ReturnStatus-файл (0/1/2/3/4; код возврата процесса
не используется — грабля из спайков). VAParams-файлы (`params/`) удаляются
после батча (NFR-001: тестовый пароль не остаётся в артефактах). Лог VA —
`logs/va-<user>.log` (не читать, пока процесс пишет — грабля совместного
доступа).

### 4.8 Репортёр (FR-008, FR-009)

Чтение `allure/<user>/*-result.json` (`ЧтениеJSON`): name, status, start,
stop, labels — + ReturnStatus батча + fixtures.json → сводка:
- таблица «сценарий × пользователь × статус» (passed/failed/broken/timeout);
- покрытие: представители по осям, задействованные АРМы, coverageGaps;
- пароли: восстановлено/несоответствие;
- артефакты: пути.
Выход: `summary.json` (машиночитаемый, для диффа прогонов) + `summary.md`
(человекочитаемый, показать в форме).

### 4.9 Run-каталоги (FR-012)

`runId = <год><месяц><день>-<чч><мм><сс>`; каталог создаётся, никогда не
перезаписывается; старые остаются (D-009). `.gitignore: tests/run-*/`.

### 4.10 Настройки (NFR-004)

`tests/preprocessor-settings.json`: строка подключения (умолчание
`localhost\dev_erpapk_demo`), путь 1cv8c, путь VA EPF, базовый каталог
прогонов, таймауты, порт-диапазон. Загружается в форму при открытии,
переопределяется в форме, кнопка «Сохранить настройки» пишет обратно.
Перенос на другую базу = правка файла, код не меняется.

| Платформа 8.5: ПользователиИнформационнойБазы | хэши паролей, сопоставление | сервер, админ | попытка/исключение, восстановление в finally |
| ERP: Справочник.Пользователи | авторы → ИБ-пользователи | чтение | несопоставленный → исключение с предупреждением |
| Файловая система | run-каталог, шаблоны, карта, настройки | чтение/запись | ошибки ввода-вывода → сообщение, стоп фазы |

## 6. Security / Permissions / Privacy

- Запуск обработки — проверка `Пользователи.ЭтоПолноправныйПользователь()`
  + административные права; иначе — отказ с сообщением (NFR-001).
- Хэши паролей читаются и пишутся только внутри сеанса обработки, не
  попадают в fixtures/логи/отчёты/VAParams.
- Тестовый пароль: случайный на прогон (`ГенераторСлучайныхЧисел`), живёт
  в памяти сеанса и во временном VAParams-файле, который удаляется после
  батча; в логи/сводку не пишется.
- Данные прогона (fixtures.json) содержат только бизнес-документы
  тестовой базы — без кредов.

## 7. UX Notes

Форма (одна, вкладки-секции):
1. «Отбор и сканирование»: фильтры (организация, период, виды документов,
   пользователи), кнопки «Сканировать документы» → ТЧ представителей.
2. «План прогона»: ТЧ план (пользователь × сценарий × документ × АРМ),
   галочки исключения шаблонов, сводка плана (кол-во батчей, оценка
   времени), «Запустить прогон (подменяет пароли)» + подтверждение.
3. «Отчёт»: сводка после прогона (таблица статусов, покрытие, пароли),
   кнопка «Сформировать отчёт» (пересборка из артефактов).
Прогресс: статусная строка «батч 3/7, пользователь X…», лог в
`preprocessing.log`. Пустые состояния: «ничего не найдено — ослабьте
фильтры»; «нет сопоставленных авторов — список».

## 8. Edge Cases

| Случай | Поведение |
|---|---|
| Ничего не найдено | пустые ТЧ + подсказка; прогон не активен |
| Автор не сопоставлен / ИБ-пользователь заблокирован | исключён из плана, предупреждение (FR-003) |
| У автора пароль не установлен | прогон без подмены, пометка (D-007) |
| Таймаут батча | kill-tree, статус «timeout», восстановление хэша, следующий батч (FR-009) |
| ReturnStatus=2/3/4 | диагноз в сводке (подключение/нет сценариев/компонента), батч «broken» |
| Восстановленный хэш ≠ сохранённый | «mismatch» в сводке, критическая строка, прогон продолжается |
| Один автор — несколько типов документов | несколько сценариев в одном батче пользователя |
| Пробел покрытия (нет представителя значения оси) | строка в coverageGaps плана и отчёта (FR-016) |
| Второй запуск обработки параллельно | блокировка: флаг-файл в базовом каталоге прогонов |
| Пользователь уже в активном сеансе базы | предупреждение перед запуском (сеанс TestClient под тем же именем) |
| `ДатаУстановкиПароля` после восстановления | остаётся датой тестового пароля — принято (FAQ, спайк) |

## 10. Development Sequencing

1. Scaffold EPF + форма (epf-init-паттерн), compile-gate — без зависимостей.
2. Сканер + селектор + сопоставление пользователей (§4.1–4.2) + ТЧ формы.
3. Экстрактор fixtures.json + coverage-map.json v1 (5 документов).
4. Генератор feature + первый шаблон (smoke-эталон).
5. Менеджер паролей + раннер VA (один батч) — ReturnStatus=0.
6. Репортёр + сводка + покрытие.
7. Мульти-батч, таймаут/kill, частичный сбой; smoke E2E всего цикла.

## 11. Testing / Verification Strategy

- **Гейты после каждой правки BSL**: `bsl-ls` MCP `bsl_analyze` (≠ «0
  файлов») + `v8std` MCP — до загрузки в базу.
- **Compile-gate**: сборка EPF (epf-build) → `ПодключитьВнешнююОбработку` +
  `ПолучитьФорму` без исполнения (epf-run-debug).
- **Smoke-батч**: 1 пользователь × smoke-фича → ReturnStatus=0, allure
  result.json на месте, хэш восстановлен (смоук-эталон спайков, 84–103 с).
- **Полнота фикстур (FR-002)**: smoke-шаблон заполняет документ целиком из
  fixtures.json — шаги не падают на «поле не заполнено».
- **E2E**: полный цикл на dev_erpapk_demo ≥2 пользователей, ≥2 типов
  документов, ≥2 АРМ-сценариев; проверка summary.json и восстановления
  паролей (вход под исходным паролем).
- Команды: `python scripts/pre_load_validate.py` (после правок XML),
  powershell db-load-xml (для тест-базы при round-trip).

## 12. Observability

- `preprocessing.log` — события фаз (скан/отбор/фикстуры/батчи/восстановление) с таймстампами.
- `logs/va-<user>.log` — вывод VA per батч.
- `summary.json` — машиночитаемый итог (дифф прогонов после «обновлений релиза»).
- Прогресс в форме — счётчики батчей/сценариев.

## 13. Migration / Rollout

- Перенос на другую тестовую базу: правка `preprocessor-settings.json`
  (строка подключения) — код не меняется (NFR-004).
- Обновление релиза ERP/АПК: сверка coverage-map с новыми исходниками
  (оси/АРМы/поля); пробелы покажет отчёт прогона.
- Rollback: обработка внешняя — отключение/удаление EPF; данные базы не
  тронуты (кроме тестовых документов, вводимых сценариями).

## 14. Technical Decisions

### TD-001: Карта покрытия — внешний JSON в репо, не в метаданных
- **Decision:** `tests/coverage-map.json` версионируется в git, загружается обработкой.
- **Why:** правится без пересборки EPF; виден в ревью; переносим (NFR-004).
- **Trade-off:** файл надо доставлять рядом с обработкой при переносе.
- **Alternatives:** реквизиты обработки (пересборка на каждую правку карты); справочник в базе (меняет базу — запрещено).

### TD-002: Селектор — детерминированный «первый по МоментуВремени»
- **Decision:** представитель группы = документ с минимальным `МоментВремени`.
- **Why:** воспроизводимость прогонов; без случайности.
- **Trade-off:** «старые» данные могут отставать от текущего релиза — закрывается тем, что данные — только элементы заполнения, ввод текущим месяцем.
- **Alternatives:** случайный/последний документ — невоспроизводимо/старее некуда.

### TD-003: Запуск и надзор VA — WScript.Shell.Exec + taskkill /T
- **Decision:** батч запускается через `cmd /c` (PID оболочки), ожидание с таймаутом, kill-tree через `taskkill`.
- **Why:** 1С не даёт PID/kill запущенных процессов; Exec возвращает PID; `cmd /c` позволяет убить всё дерево (1cv8c + TestClient).
- **Trade-off:** Windows-only, COM WScript.Shell (тонкий клиент Windows — целевая среда).
- **Alternatives:** python-раннер рядом (лишняя зависимость окружения); блокирующий `ЗапуститьПриложение` (нет таймаута).

### TD-004: Батч = пользователь, порт уникальный
- **Decision:** один TestClient-сеанс на батч; порты — последовательные из диапазона настроек.
- **Why:** изоляция прав; подтверждённый спайком паттерн; меньше подключений.
- **Trade-off:** длинные батчи у «многосторонних» пользователей — таймаут на батч настраивается.
- **Alternatives:** батч = пользователь × фича (много накладных на подключение).

### TD-005: Тестовый пароль — случайный на прогон, только в памяти + временный VAParams
- **Decision:** генерировать на прогон; VAParams-файлы удаляются после батча; в логи/сводку не пишется.
- **Why:** NFR-001 (секреты не в артефактах).
- **Trade-off:** невозможно «повторить батч руками» без повторной подмены — FAQ: как повторить.
- **Alternatives:** фиксированный тестовый пароль (палится в артефактах).

### TD-006: Вердикт — только ReturnStatus-файл
- **Decision:** ReturnStatus 0–4 — единственный вердикт батча; строка /Out не парсится.
- **Why:** спайки: строка может быть пуста, код возврата процесса всегда 0.
- **Trade-off:** нет деталей внутри батча — детали берём из allure result.json.

### TD-007: Сопоставление авторов — платформенный API, не БСП-обёртки
- **Decision:** `ИдентификаторПользователяИБ` + `ПользователиИнформационнойБазы.НайтиПоИдентификатору()`.
- **Why:** минимум зависимостей от версий БСП; подтверждено исходниками ERP.
- **Trade-off:** при смене механизма сопоставления в ERP — правка одного блока.

### TD-008: Шаблоны — простой плейсхолдер `{{path}}`, подстановка в 1С
- **Decision:** без внешних шаблонизаторов.
- **Why:** самодостаточность сценариев (D-002), отладка в UI VA.
- **Trade-off:** нет условной логики в шаблонах — варианты покрытия = отдельные шаблоны/сценарии.

### TD-009: ЗОД — параметр VAParams
- **Decision:** отключение ЗОД-предупреждений на прогон через VAParams (имя параметра уточнить по JsonParamsRU.md при реализации; спайк отключал настройкой).
- **Why:** TestClient не должен блокироваться интерактивом (FR-010).
- **Trade-off:** глобальная настройка пользователя меняется на прогон — вернуть после (учтено в менеджере паролей как атрибут пользователя).

| Риск | Вер-ть | Влияние | Митигация |
|---|---|---|---|
| WScript.Shell недоступен в среде клиента | Low | High | проверка при запуске, внятная ошибка; среда — Windows-клиент, спайком COM подтверждён |
| Имена параметров VAParams меняются между версиями VA | Medium | Medium | VA-версия зафиксирована; параметры сверены со спайками; проверка на smoke-батче |

| Зависание TestClient без таймаута процесса | Low | High | таймаут на каждый батч + kill-tree (TD-003) |
| Сценарий оставляет введённые тестовые документы | High | Low | тестовая база; политика очистки — вне релиза 1 (Non-Goals) |

## 16. Implementation FAQ

**Q:** Как повторить упавший батч вручную?  
**A:** В run-каталоге лежат фичи и логи; VAParams восстанавливается кнопкой
«Сформировать прогон» для этого батча (без пароля — подставить вручную или
повторить с подменой через обработку).

**Q:** Что если у пользователя ИБ включена блокировка?  
**A:** Исключается из плана с предупреждением (§4.2).

**Q:** Почему `ДатаУстановкиПароля` «сдвинулась»?  
**A:** Платформа не откатывает её при восстановлении хэша (спайк). Если
критично — восстановление `ЗаписываемаяДатаУстановкиПароля` (не входит в
релиз 1).

**Q:** Как добавить новый тип документа (релиз 2)?  
**A:** coverage-map: `fieldList` + `axes` + `arms`; шаблон
`tests/templates/`; поле в сканере (список типов — из coverage-map).

**Q:** Почему план содержит АРМ, «не относящийся» к документу?  
**A:** `arms[].when` в coverage-map; если условие не выполняется по осям
документа-представителя — АРМ не включается; спорные условия правятся в
карте (файл, без пересборки).
