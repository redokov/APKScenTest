# Feature: 001 — Обработка препроцессинга (сценарные регресс-тесты АПК 2.5)

> Status: Approved
> Source: `.ai/sdd/PLAN.md` (Фаза 2), решения D1–D7; `docs/fixture-model.md`; спайки `docs/spike-*.md`
> Last Updated: 2026-10-11

## Overview

Внешняя обработка (EPF) для 1С:ERP + АПК 2.5, запускаемая **всегда от
администратора**. После обновления релиза ERP/АПК на тестовой базе админ
одной обработкой: сканирует введённые документы растениеводства, отбирает минимально разумный
набор, покрывающий варианты обработки, → извлекает
из них элементы заполнения сценариев (фикстуры) и пользователей-авторов →
генерирует feature-файлы, которые под правами авторов выполняют **ввод и
проведение** документов на основе фикстур и **отражение отраслевого учёта
в управленческий/бухгалтерский через соответствующие АРМы** — всё текущим
месяцем → временно
подменяет пароли пользователей ИБ (без знания реальных паролей, через
сохранение/восстановление хэша) → прогоняет сценарии Vanessa Automation →
собирает отчёт о покрытии и статусах «сценарий × пользователь × статус»
(Allure-каталог VA + собственная сводка).

Отображение найденных документов — не самоцель: сканирование нужно, чтобы
(а) извлечь фикстуры, (б) построить план покрытия «вариант обработки → документ-представитель →
сценарии ввода/проведения → АРМ → пользователь», (в) определить
пользователей прогона. Отборы (фильтры) — только средство уменьшить объём
тестов, когда полный прогон не нужен.

## Business Context

- **Problem:** после обновления релиза ERP/АПК нет быстрого способа узнать,
  какие бизнес-сценарии растениеводства сломались. Ручная проверка под
  правами реальных пользователей требует знания их паролей.
- **Users:** администратор/инженер по тестированию тестовой базы
  (единственный оператор обработки; запуск только под админом).
- **Value:** one-command регресс-отчёт по релизу; проверка под реальными
  правами без раскрытия паролей.
- **Success signal:** после обновления релиза на dev_erpapk_demo прогон
  завершается за разумное время, отчёт показывает статусы всех сценариев
  по всем пользователям, пароли пользователей аутентично восстановлены.

## Goals

- Полный цикл «сканирование → фикстуры → генерация сценариев → прогон под
  пользователями → отчёт» из одной формы обработки.
- Покрытие: каждый вариант обработки целевых документов (направления
  затрат, виды ТС и другие критерии покрытия) представлен документом-
  представителем и покрыт сценарием ввода/проведения под правами автора
  **и** отражением через соответствующий АРМ; покрытие видно в плане и отчёте.
- Прогон под правами авторов найденных документов, без знания их паролей.
- Гарантированное восстановление исходных паролей при любом исходе прогона.
- Воспроизводимость: артефакты прогона (fixtures.json, run-каталог, allure,
  логи) сохраняются на диск и позволяют понять, что именно гонялось.

## Non-Goals / Out of Scope

- Содержимое сценариев растениеводства (шаги, проверки движений) — **спека 002**.
- Веб-клиент как тест-клиент (требует публикации базы) — Фаза 4 (D7).
- allure-commandline и HTML-отчёт Allure — не ставим (D3), только каталог
  результатов + собственная сводка.
- Придумывание тестовых данных: элементы заполнения сценариев берутся
  только из реальных документов базы. Сами сценарии выполняют ввод и
  проведение тестовых документов на основе этих данных (тестовая база);
  политика очистки созданных документов после прогона — решение design/спеки 002.
- Животноводство и прочие модули АПК вне растениеводства — релиз 1 не
  покрывает (АРМы отражения тестируются в объёме документов растениеводства).
- Хранение/передача реальных паролей или их хэшей вне информационной базы.

## User Stories

### US-001: Регресс-прогон после обновления релиза

**As a** администратор тестовой базы
**I want to** одной обработкой прогнать сценарные тесты растениеводства
по документам базы и получить отчёт со статусами
**So that** сразу после обновления релиза я вижу, что сломалось

**Acceptance Criteria:**
- [ ] Обработка находит целевые документы и отбирает минимально разумный
      набор представителей, покрывающий варианты обработки
- [ ] Для каждого документа-представителя сценарии выполняют его ввод и
      проведение (текущим месяцем) с извлечёнными данными под правами автора
- [ ] Для каждого варианта обработки задействован соответствующий АРМ
      отражения (отраслевой → управленческий/бухгалтерский), текущим месяцем
- [ ] Итог — сводка «сценарий × пользователь × статус» + карта покрытия
      (варианты обработки, АРМы, пробелы) + allure-каталог
- [ ] После прогона все исходные пароли пользователей работают как раньше

### US-002: Отбор данных для прогона

**As a** администратор
**I want to** по умолчанию получить полный план покрытия по всем найденным
документам, а фильтры (организация, период, виды документов, пользователи,
конкретные документы) применять только когда нужно уменьшить объём тестов
**So that** полный регресс не требует настроек, а ускоренный срез задаётся
явно

**Acceptance Criteria:**
- [ ] Без дополнительных фильтров план охватывает все варианты обработки
      целевых документов независимо от дат их ввода в базе
- [ ] Любой фильтр только сужает план (уменьшает объём), полный охват —
      состояние по умолчанию
- [ ] Результат сканирования показывается как план покрытия «документ →
      сценарии ввода/проведения → АРМ → пользователь», а не просто список
      документов
- [ ] Прогон запускается только по подтверждённому плану

### US-003: Безопасность паролей

**As a** владелец учётной записи тестовой базы
**I want to** чтобы мой пароль не раскрывался и после прогона остался прежним
**So that** мои права не скомпрометированы и учётка продолжает работать

**Acceptance Criteria:**
- [ ] Обработка не запрашивает и не хранит реальные пароли пользователей
- [ ] На время прогона пароль временно заменяются тестовым, после —
      восстанавливаются из сохранённого хэша
- [ ] Восстановление выполняется и при падении/таймауте прогона
- [ ] Тестовый пароль нигде не сохраняется в отчётах/логах-артефактах

## Functional Requirements

### FR-001: Сканер документов АПК — Must Have

WHEN администратор запускает сканирование
IF дополнительные фильтры не заданы
THE SYSTEM SHALL найти все проведённые документы растениеводства релиза 1
(АпкПутевойЛистТракториста, АпкПутевойЛистАвтотранспорта,
АпкНарядНаСдельнуюРаботу, АпкЗаправочныеВедомости,
АпкРегистрацияВзвешиванийНаТоку) без ограничения по датам ввода
IF заданы фильтры (организация, период, виды документов, пользователи,
конкретные документы)
THE SYSTEM SHALL сузить выборку до удовлетворяющих им
SO THAT даты документов в базе не влияют на охват, а фильтры служат
только уменьшению объёма тестов.

### FR-002: Извлечение фикстур — Must Have

WHEN отобраны документы-представители (FR-016)
THE SYSTEM SHALL сформировать по ним фикстуры, достаточные для сценарного
ввода и проведения каждого документа (все элементы заполнения по модели
`docs/fixture-model.md`: организация, подразделение, номенклатура, техника,
ответственные, авторы; данные шапки и до 3 строк каждой табличной части) и
записать их в файл `fixtures.json` run-каталога
SO THAT шаблон сценария заполняет документ целиком из фикстуры, без
ручного подбора данных.

Достаточность фикстуры (все поля, требуемые шаблоном сценариев данного
типа документа) проверяется на smoke-прогоне.

### FR-003: Сопоставление «автор документа → пользователь ИБ» — Must Have

WHEN сканирование нашло документы
THE SYSTEM SHALL для каждого автора (Справочник.Пользователи) определить
соответствующего пользователя ИБ стандартным механизмом сопоставления ERP
SO THAT сценарии запускаются под правами автора.

IF автор не сопоставлен ни с одним пользователем ИБ
THE SYSTEM SHALL исключить его из плана прогонов и показать предупреждение
в форме и отчёте.

### FR-004: План прогонов и его подтверждение — Must Have

WHEN фикстуры сформированы
THE SYSTEM SHALL построить и показать план покрытия «пользователь × документ-представитель
× сценарии (ввод/проведение + АРМ отражения)» и ждать явного запуска
оператором
SO THAT оператор видит, что именно будет проверено, и деструктивная фаза
(подмена паролей) начинается только по подтверждению.

### FR-005: Генерация feature-файлов из шаблонов — Must Have

WHEN план прогонов подтверждён
THE SYSTEM SHALL сгенерировать feature-файлы run-каталога из шаблонов
`tests/templates/*.feature` подстановкой данных из фикстур
(имена форм — по метаданным; данные — из фикстур; пользователь прогона —
из плана; шаги сценариев выполняют ввод и проведение документов на основе
данных фикстур, датой текущего месяца) и записать их в run-каталог вне данных ИБ
SO THAT прогоны воспроизводимы и не зависят от ручного редактирования.

### FR-006: Подмена и восстановление пароля — Must Have

WHEN начат прогон под пользователем
IF у пользователя установлен пароль
THE SYSTEM SHALL сохранить хэш пароля (`СохраняемоеЗначениеПароля`),
установить тестовый пароль, прогнать сценарии, затем восстановить хэш —
и выполнить восстановление гарантированно при любом исходе прогона
(ошибки сценариев, таймаут, падение процесса)
SO THAT исходный пароль пользователя сохраняется.

IF у пользователя пароль не установлен
THE SYSTEM SHALL прогонять сценарии без подмены пароля и пометить это
в плане и отчёте.

### FR-007: Прогон Vanessa Automation под пользователем — Must Have

WHEN выполняется прогон по плану
THE SYSTEM SHALL для каждой пары «пользователь × набор сценариев» запустить
Vanessa Automation с параметрами: TestManager — под администратором,
TestClient — под целевым пользователем (тестовый пароль), и получить
вердикт прогона по официальному статус-файлу VA (ReturnStatus)
SO THAT результат прогона определяется надёжно, а не по строкам лога.

THE SYSTEM SHALL применять таймаут на каждый запуск и принудительно
завершать дерево процессов при его превышении.

### FR-008: Отчёт прогона — Must Have

WHEN прогон завершён (полностью или частично)
THE SYSTEM SHALL сформировать сводку «сценарий × пользователь × статус»
из allure-результатов VA и fixtures.json, показать её в форме и сохранить
в отчёт-артефакт run-каталога вместе с логами
SO THAT оператор видит итоги и может разобрать падения.

### FR-009: Отчёт при частичном сбое — Must Have

IF часть прогонов завершилась таймаутом или падением
THE SYSTEM SHALL отметить их в сводке как не выполненные, продолжить
остальные и в конце гарантированно восстановить все пароли
SO THAT один сбой не рушит весь регресс и не оставляет подменённых паролей.

### FR-010: Отключение ЗОД-предупреждений на прогон — Should Have

WHEN выполняется прогон
THE SYSTEM SHALL отключать для сеансов прогона предупреждения
«запуск от имени другого пользователя» (ЗОД)
SO THAT TestClient не блокируется интерактивными предупреждениями.

### FR-011: Выбор сценариев для прогона — Should Have

WHEN оператор формирует план
THE SYSTEM SHALL позволять исключить отдельные шаблоны сценариев из прогона
SO THAT можно гнать только нужный срез.

### FR-012: Хранение артефактов прогона — Should Have

WHEN существуют run-каталоги прошлых прогонов
THE SYSTEM SHALL сохранять их не перезаписывая (run-каталог на запуск,
уникальное имя), а allure-результаты каждого запуска — в отдельный
подкаталог сборки
SO THAT прогоны сравнимы между собой.

### FR-013: Веб-клиент как тест-клиент — Won't Have

Веб-клиент не поддерживается в релизе 1 (Фаза 4, D7). Тест-клиент — тонкий.

### FR-014: HTML-отчёт allure-commandline — Won't Have

Не ставим (D3): только каталог allure-результатов + собственная сводка.

### FR-015: Покрытие АРМами отражения — Must Have

WHEN построен план покрытия
THE SYSTEM SHALL для каждого отобранного документа-представителя включить
в план сценарии
АРМа отражения, которым этот документ обрабатывается (отражение отраслевого
учёта в управленческий и бухгалтерский контуры — текущим месяцем; карта
соответствия «вариант обработки → АРМ» ведётся в решении и заполняется по
документации АПК и исходникам модуля)
SO THAT регресс проверяет не только ввод/проведение документов, но и их
отражение в учёте.

IF в базе нет документов, обрабатываемых некоторым АРМом
THE SYSTEM SHALL не включать сценарии этого АРМа в план и показать в
отчёте фактическое покрытие АРМов
SO THAT покрытие АРМов следует данным базы и пустые АРМы не гоняются.

### FR-016: Отбор документов-представителей по критериям покрытия — Must Have

WHEN сканирование нашло документы
THE SYSTEM SHALL для каждого типа документов отобрать минимально разумный
набор представителей, покрывающий все варианты его обработки — по
критериям покрытия данного типа (классификационные реквизиты, ведущие к
разной обработке: например, для путевого листа тракториста — направление
затрат: вид ПР → АРМ отражения выпуска продукции растениеводства, вид
ОХР → другой АРМ; для заправочной ведомости — легковые, грузовые
автомобили, тракторы) — и строить фикстуры и план по отобранному набору,
не дублируя однотипные документы
SO THAT прогон минимален по объёму при полном функциональном покрытии.

IF в базе нет документа-представителя для некоторого варианта обработки
THE SYSTEM SHALL показать пробел покрытия в плане и отчёте.

## Non-Functional Requirements

### NFR-001: Безопасность / приватность

- Запуск обработки — только от администратора ИБ; при запуске без прав —
  внятный отказ.
- Реальные пароли и их хэши не покидают информационную базу: не пишутся
  в fixtures.json, отчёты, логи, параметры запуска.
- Тестовый пароль — одноразовый, не фиксируется в артефактах прогона.

### NFR-002: Надёжность

- Восстановление паролей — гарантированное (finally-семантика), для всех
  пользователей из плана, при любом исходе прогона (FR-006, FR-009).
- Верификация восстановления: после прогона обработка проверяет, что
  исходный хэш на месте, и отражает это в сводке.

### NFR-003: Производительность

- Смоук-прогон (1 сценарий × 1 пользователь) укладывается в таймаут
  5 минут (замер спайков: 84–103 с).
- Таймаут всего прогона и каждого запуска — настраиваемые параметры.

### NFR-004: Переносимость

- Обработка переносится на другую тестовую базу того же релиза без правки
  кода: строка подключения, пути VA/шаблонов/каталогов прогона — параметры
  обработки (умолчания из настроек, переопределяемые в форме).

### NFR-005: Качество кода (процессные гейты)

- Любая правка BSL проходит гейты bsl-ls (`bsl_analyze`, ≠ «0 файлов»)
  и v8std до загрузки в базу.
- Сборка EPF проходит compile-gate (подключение обработки + получение формы
  без исполнения).
- Смоук-прогон (FR-007 на smoke-фиче) — обязательный приёмочный шаг.

## User Experience Notes

- Одна форма: сверху — фильтры и команда «Сканировать документы»;
  в середине — результат сканирования (документы, авторы, план прогонов);
  снизу — команды «Сформировать прогон», «Запустить прогон (подменяет
  пароли)», «Сформировать отчёт».
- Обработка: `АпкПодготовкаСценарныхТестов` (синоним «Подготовка
  сценарных тестов АПК») — D-010.
- Перед запуском — явное подтверждение (фаза меняет пароли пользователей).
- Пустые состояния: «документы не найдены» с подсказкой о фильтрах;
  «авторы не сопоставлены» — список с причиной исключения.
- Долгие операции показывают прогресс и логируются на диск.

## Constraints

- Платформа 8.5.4.1683; база `localhost\dev_erpapk_demo` (PostgreSQL).
- Vanessa Automation single 1.2.043.42; вердикт — только ReturnStatus-файл.
- Конфигуратор базы — только автономный режим (designer agent), его процесс
  не трогать.
- Кириллица в CLI — только через python-билдеры; имена feature-файлов —
  латиницей.
- Прогон сериализован (один TestManager-запуск в момент времени, свой порт).

## Decisions

### D-001: Препроцессинг — внешняя обработка (EPF)

**Decision:** реализуем как EPF, исходники XML в `src/`, сборка epf-build.
**Reason:** решение плана D1; не трогаем конфигурацию/расширения базы.
**Source:** PLAN.md D1
**Impacts:** весь Feature 001

### D-002: Сценарии — генерация .feature из шаблонов + fixtures.json

**Decision:** шаблоны `tests/templates/*.feature` с плейсхолдерами;
препроцессинг подставляет данные и пишет run-каталог + fixtures.json.
**Reason:** решение плана D2; сценарии самодостаточны, отлаживаются в UI VA.
**Source:** PLAN.md D2 → FR-002, FR-005
**Impacts:** FR-002, FR-005

### D-003: Отчёт — allure-каталог VA + собственная сводка

**Decision:** allure-commandline не ставим; сводка парсит allure
result-json + fixtures.json.
**Reason:** решение плана D3; достаточно для «что сломалось после релиза».
**Source:** PLAN.md D3 → FR-008
**Impacts:** FR-008, FR-014

### D-004: Фикстуры — шапка + до 3 строк каждой табличной части

**Decision:** в fixtures.json хранить данные шапки и не более 3 строк
каждой табличной части на документ.
**Reason:** баланс полноты и скорости прогона; предложение из
fixture-model.md, критических возражений нет.
**Source:** fixture-model.md «Открытые вопросы»
**Impacts:** FR-002

### D-005: Даты документов не важны; ввод и отражение — текущим месяцем

**Decision:** сканирование ищет целевые документы без ограничения по
датам ввода (период — опциональный фильтр уменьшения объёма). Сценарии
вводят новые документы и выполняют отражение через АРМы **текущим
месяцем**; фильтры организации/видов документов/пользователей/конкретных
документов — опциональные сужения только для уменьшения объёма тестов.
**Reason:** указание пользователя: не важно, за какие даты введены
документы в базе; проведение текущим месяцем не трогает закрытые периоды
и даёт единый проверяемый срез отражения. Отборы нужны только для
уменьшения объёма (D5).
**Source:** обратная связь пользователя на draft, PLAN.md D5
**Impacts:** FR-001, FR-005, FR-015, US-002

### D-006: Сопоставление авторов — стандартный механизм ERP

**Decision:** пользователь ИБ определяется по стандартному реквизиту
сопоставления справочника «Пользователи» ERP (идентификатор пользователя ИБ);
несопоставленные авторы исключаются с предупреждением.
**Reason:** реальные авторы уже сопоставлены (спайк user-run); свой механизм
не нужен. Точное имя реквизита уточняется по исходникам ERP на этапе design.
**Source:** fixture-model.md «Открытые вопросы»
**Impacts:** FR-003

### D-007: Пользователи без пароля — прогон без подмены

**Decision:** если у пользователя ИБ пароль не установлен, прогон выполняется
без подмены; в плане и отчёте — пометка «без пароля».
**Reason:** подмена не нужна, лишние операции с хэшем не выполняем.
**Source:** US-003
**Impacts:** FR-006

### D-008: Пакетирование прогонов — один запуск VA на пользователя

**Decision:** сценарии одного пользователя гоняются одним запуском VA
(один TestClient-сеанс на пакет); allure-подкаталог на запуск.
**Reason:** меньше накладных расходов на подключение TestClient; изоляция
прав пользователя; подтверждённый паттерн спайков.
**Source:** spike-user-run.md
**Impacts:** FR-007, FR-012

### D-009: Run-каталоги и allure-сборки не перезаписываются

**Decision:** каждый прогон пишет свой run-каталог; allure — базовый каталог
+ подкаталог сборки на запуск.
**Reason:** сравнимость прогонов после разных «обновлений релиза».
**Source:** spike-allure.md (структура allure-выгрузки)
**Impacts:** FR-012

### D-010: Имя обработки

**Decision:** имя метаданных — `АпкПодготовкаСценарныхТестов`, синоним —
«Подготовка сценарных тестов АПК».
**Reason:** понятность без жаргона «препроцессор»; системный префикс «Апк».
**Source:** Q-001 (выбор пользователя, вариант B)
**Impacts:** User Experience Notes, Форма обработки, будущий runbook (Фаза 4)

### D-011: Названия команд в форме

**Decision:** «Сканировать документы» · «Сформировать прогон» ·
«Запустить прогон (подменяет пароли)» · «Сформировать отчёт».
**Reason:** глаголы фаз; явная маркировка деструктивной фазы (подмена паролей).
**Source:** Q-002 (выбор пользователя, вариант A)
**Impacts:** FR-001, FR-004, FR-005, FR-008, User Experience Notes

### D-012: АРМы отражения — в скоупе релиза 1

**Decision:** для каждого найденного документа в план включаются сценарии
АРМа отражения, которым он обрабатывается; карта «тип документа → АРМ»
определяется при разработке из документации АПК и исходников модуля
(APKModSrc, вики АПК) и ведётся в решении. Нет документов — АРМ не
гоняется (покрытие следует данным базы).
**Reason:** указание пользователя: без АРМов отражения регресс неполный —
ввод/проведение документа бесполезно, если его данные не попадают в
управленческий/бухгалтерский учёт.
**Source:** обратная связь пользователя на draft requirements
**Impacts:** FR-002, FR-004, FR-015, Success Metrics, Non-Goals

### D-013: Детализация данных фикстур — на design/спеку 002

**Decision:** перечень извлекаемых полей зафиксирован в
`docs/fixture-model.md` (реквизиты и ТЧ пяти типов документов); требования
закрепляют критерий достаточности (шаблон заполняет документ целиком из
фикстуры, проверяется smoke-прогоном). Уточнение структуры JSON, карты
«документ → АРМ» и перечня полей под конкретные шаги — design.md (спека 001)
и сценарии (спека 002).
**Reason:** вопрос пользователя о детализации данных; на уровне требований
важен критерий достаточности, состав полей — техническая деталь.
**Source:** обратная связь пользователя на draft requirements
**Impacts:** FR-002

### D-014: Минимально разумный набор данных — покрытие вариантов обработки

**Decision:** план строится не на всех найденных документах, а на отобранных
документах-представителях: для каждого типа документов задаются критерии
покрытия — классификационные оси, значения которых ведут к разной
обработке (направление затрат ПР/ОХР/… у путевого листа тракториста →
разные АРМы; виды транспортных средств у заправочной ведомости:
легковые/грузовые/тракторы; и т.д.). Критерии формулируются при разработке
по документации АПК и исходникам модуля и фиксируются в карте покрытия
решения; однотипные дубли в прогон не включаются.
**Reason:** указание пользователя: полное дублирование всех найденных
документов не даёт новой информации; покрытие определяется вариантами
обработки, а не количеством документов.
**Source:** обратная связь пользователя на draft requirements
**Impacts:** FR-002, FR-004, FR-015, FR-016, Success Metrics

## Glossary

- **Препроцессинг** — обработка, готовящая и запускающая сценарные прогоны.
- **Фикстура** — извлечённые из документов данные для подстановки в сценарии.
- **Run-каталог** — каталог артефактов одного прогона (feature-файлы,
  fixtures.json, allure, логи, сводка).
- **TestManager / TestClient** — сеансы VA: менеджер тестирования (админ) и
  управляемый клиент тестирования (целевой пользователь).
- **ReturnStatus** — официальный файл-вердикт VA: 0 ок, 1 ошибки сценариев,
  2 проблемы TestClient, 3 нет сценариев, 4 не встала компонента.
- **ЗОД** — предупреждение «запуск от имени другого пользователя».
- **АРМ отражения** — АРМ подсистемы АПК для отражения данных отраслевого
  учёта в управленческий и бухгалтерский контуры.
- **Хэш пароля** — `СохраняемоеЗначениеПароля` пользователя ИБ.
- **Документ-представитель** — документ, отобранный как покрытие одного
  варианта обработки типа документов; однотипные дубли не гоняются.
- **Критерий покрытия** — классификационная ось типа документов, значения
  которой ведут к разной обработке (разным АРМам): направление затрат,
  вид транспортного средства и т.п.
