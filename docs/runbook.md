# Runbook: регресс-прогон после обновления релиза (спека 003)

Одна команда проверяет сценарии растениеводства на `dev_erpapk_demo`
после «обновления» (или без него — репетиция) и откатывает базу в
исходное состояние. Время: репетиция ≈ 33 мин, с обновлением ≈ 46 мин
(dump ~4 мин + update ~14 мин + E2E ~14 мин + rollback ~13 мин).

## 1. Что нужно до запуска

- Платформа `C:\Program Files\1cv8\8.5.4.1683\bin\1cv8.exe`, база
  `localhost\dev_erpapk_demo` доступна (проверяется автоматически, COM).
- **Никаких активных сеансов в базе на моменты Dump/RestoreIB** —
  RestoreIB требует монопольного доступа. Фоновые задания (DefUser,
  BackgroundJob) МОГУТ заблокировать эксклюзив (подтверждено 19.10:
  дамп ждал 900 с, aborted) — обёртка автоматически включает
  `scheduled-jobs-deny=on` на время прогона и возвращает исходное
  значение после отката. Чужие интерактивные сеансы всё равно
  завершить вручную (режим «Все функции» или rac:
  `rac session list --cluster=67cdef87-7bfc-4dae-b8e4-3ea9f8529156`).
- Свободное место ≥ 5 ГБ (dt-дамп 1.7 ГБ, минимум ×2 с запасом).
- Артефакт «обновления» (для `--update`): файл `.cf` (конфигурация
  релиза) или `.dt` (полная демо-база релиза). Путь передаётся команде.

## 2. Запуск

```bash
# Репетиция (без обновления): дамп -> E2E-гейт -> откат -> отчёт
python scripts/regress_run.py --rehearsal

# После обновления релиза: дамп -> применить обновление -> гейт -> откат -> отчёт
python scripts/regress_run.py --update C:\путь\к\релизу.cf     # или .dt

# С эталонным состоянием базы (TD-007): дамп -> RestoreIB baseline-dt
# -> E2E-гейт -> откат к дампу текущего (~47 мин)
python scripts/regress_run.py --rehearsal --baseline-dt tmp/regress/20261019-052456/pre-update.dt
```

**`--baseline-dt` (TD-007)** — старт гейта с идентичного известного-хорошего
состояния базы; защита от деградации демо-базы (§7). Порядок фаз: дамп
текущего → RestoreIB baseline-dt → гейт → откат к дампу текущего
(finally, при любом исходе). Файл baseline-dt НЕ удаляется.
`--baseline-dt` + `--update` — отказ до дампа (exit 2, RestoreIB затёр
бы обновление); `--baseline-dt` без `--rehearsal` — отказ (exit 2).

**Снять свежий baseline-dt**: после ЗЕЛЁНОГО прогона с обновлением
скопировать его `tmp/regress/<ts>/pre-update.dt` в отдельное место
(напр. `tmp/regress/baseline-dt/pre-update-<дата>.dt`) и передавать
этот путь в `--baseline-dt`. Green-дамп — дамп базы ДО применения
обновления, но при здоровой базе (гейт на нём зелёный). Обновляйте
эталон после каждого принятого релиза.

Флаги:

| Флаг | Значение |
|---|---|
| `--set-baseline` | зафиксировать зелёный прогон как эталон (`tests/baseline/baseline.json`, старый → `tests/baseline/history/`) |
| `--baseline-dt FILE.dt` | RestoreIB known-good dt перед гейтом (TD-007, §7) — только с `--rehearsal`, взаимоисключаем с `--update` |
| `--no-compare` | пропустить сравнение с baseline |
| `--gate-timeout N` | override таймаута E2E (сек, по умолчанию 2700) |

Коды возврата: `0` — зелёный, регрессий нет; `1` — красный гейт или есть
REGRESSION против baseline; `2` — инфраструктурный сбой (дамп/обновление/
откат/preflight). **База откачена при любом исходе** (кроме abort до
дампа — база и не менялась).

## 3. Чтение отчёта

Артефакты прогона: `tmp/regress/<ts>/`

- `regress-report.md` — таблица «сценарий × пользователь × статус ×
  vs baseline», батчи (rs, пароли, ЗОД), фазы с таймингами, факт rollback.
- `regress-summary.json` — машинный формат (totals, phases, regressions).
- `regress.log`, `dump.log`, `update.log`, `rollback.log` — логи фаз;
  детали E2E — `tmp/t8/t8-gate.log` + run-каталог (`tests/run-*/`,
  путь в отчёте).

Колонка `vs baseline`: `=` без изменений; **`REGRESSION`** — было
passed, стало failed/broken/timeout (главный сигнал «релиз сломал»);
`IMPROVED` — наоборот; `NEW`/`MISSING` — состав сценариев изменился.
Нет baseline (первый прогон) — колонка `n/a`, сравнение со следующего
прогона (после `--set-baseline`).

## 4. Действия при сбоях

| Симптом | Что происходит | Что делать |
|---|---|---|
| `[preflight] FAIL: артефакт обновления не найден/пуст` | abort ДО дампа, exit 2 | проверить путь/тип файла (.cf/.dt) |
| `[preflight] FAIL: база недоступна` | abort, база не тронута | поднять сервер 1С/PostgreSQL |
| Дамп/restore упал, в логе про сеансы | монопольный доступ | завершить чужие сеансы, повторить команду; фоновые задания обёртка гасит сама (scheduled-jobs-deny) |
| `phase dump FAILED dt=0MB` + «База данных заблокирована… Фоновое задание» в dump.log | фоновое задание держало блокировку, дамп не получил эксклюзив за таймаут (900 с) | обёртка включает scheduled-jobs-deny автоматически; проверить `rac infobase info … scheduled-jobs-deny`, повторить запуск в окне без регл. заданий |
| `update FAILED` | обновление не применилось, откат выполнен, exit 2 | смотреть `update.log` (битый CF? несовместимость с расширением VA?) |
| Гейт красный (exit 1) | это результат регресса | отчёт: какие сценарии; REGRESSION против baseline — влияние релиза |
| `!!!! СБОЙ ОТКАТА` (exit 2) | база могла остаться в состоянии «после обновления» | **вручную**: `1cv8 DESIGNER /S localhost\dev_erpapk_demo /N<Админ> /RestoreIB "<путь из сообщения>" /Out rollback-manual.log` — путь к pre-update.dt всегда в сообщении; дампы НЕ удаляются автоматически |
| Ручной RestoreIB «висит без вывода» долго (>20 мин) | откат был убит таймаутом посреди восстановления: на базе остались зависшие сеансы (Designer/WebClient/COM), а `/Out` пишется только по завершении | НЕ убирать повторно раньше времени: `rac session list --cluster=<id>` → `rac session terminate --session=<uuid>` для всех сеансов базы, затем повторить RestoreIB с таймаутом ≥3000 с. Признак живого restore — рост БД в pg data dir и 15–20 подключений rphost→5432. Проверка целостности после: COM-запросы к справочникам. Лицензионный блок (`ELicenceNotFound` в `C:\ProgramData\1C\Licence\3.0\logs`) выглядит как «тихое зависание» — сначала смотреть лог лицензий |
| Все батчи гейта `status=connect rs=2`, web/thin-сеансы dying сразу после подключения | лицензия не выдаётся (licenceserver log: `GetLicence failed … ELicenceNotFound`; `UseCount` меньше нужного числа одновременных сеансов) | проверить `C:\ProgramData\1C\Licence\3.0\logs\licenceserver.*.log`; дождаться обновления лицензии/увеличить число мест; для сервера+web нужно ≥3 одновременных сеанса |

## 5. Обслуживание

- **Чистка дампов**: `tmp/regress/*/pre-update*.dt` (по 1.7 ГБ) — можно
  удалять после подтверждения успешного rollback; рекомендуется ОДИН
  green-дамп хранить как эталон (см. «Известные ограничения»).
- **Baseline**: `python scripts/regress_run.py --rehearsal --set-baseline`
  после зелёного прогона обновляет эталон; история —
  `tests/baseline/history/`. Baseline хранится в git (переносим).
- **Проверка diff-логики без базы**: `python scripts/test_regress_diff.py`
  (10 синтетических проверок).

## 6. Ограничения (наследие спек 001–002)

- Прогоны — только под временными зондами (АпкСценТест_Зонд1/2);
  реальные пользователи не затрагиваются (D-001).
- Быстрый прогон без дампа/отката: `python scripts/t8_gate.py`
  (гейт напрямую, ~14 мин).
- Веб-клиент: механика реализована (`--web-client`/`--web-url`, патч
  `clientType=Web`+`webUrl` в настройки гейта, веб-публикация Apache),
  но прогон веб-клиентом заблокирован лицензией среды
  (`ELicenceNotFound`, 1 одновременное место; D-006, T7 спеки 003,
  evidence: `tmp/regress/EVIDENCE-T7.md`).
- Авто-ПЛ 02-pl-auto: авто-запись РасходаТоплива `when: never`
  (пустой АпкСкладБака КАМАЗ-65115, real data).
- Период arm-шаблонов статичен (01–31.10.2026); при смене месяца фикстуры
  актуализируются вручную.

## 7. Известные ограничения демо-базы (открытие T5, 19.10.2026)

**Демо-база деградирует от повторных прогонов**: баки ТС расходуются
(каждый полный прогон ≈ −31,5 л для МТЗ-82). Симптом исчерпания: сценарий
01-pl-tractor детерминированно падает на «жду Номер», на форме ПЛ —
«Обнаружен отрицательный остаток топлива» (без модального окна).

- Временная правка (обратимая): заправочная ведомость
  `НВЦБ-000004` (700 л Дизтопливо, от 18.10.2026, Склад ГСМ → бак
  МТЗ-82-79). Запас ≈ 18 прогонов; при повторении симптома — создать
  аналогичную ведомость **датой ранее дня прогона** (форма читает
  остаток на начало дня).
- Структурное решение (**реализовано**, TD-007): опция
  `--baseline-dt <file>` — восстановление green-дампа перед прогоном
  (`--rehearsal --baseline-dt …`, см. §2). Эталон обновлять после
  каждого зелёного прогона с обновлением.
