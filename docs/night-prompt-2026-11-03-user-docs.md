# Ночной промт: пользовательская документация релиза (раннер + сценарии)

Контекст: релизуем чистый 1С-комплект `dist/` (препроцессор EPF, раннер
EPF, Vanessa single, 27 сценариев) для тестирования сторонних решений
заказчика. Комплект работает целиком в сеансе 1С, БЕЗ python/COM/LLM.
Не хватает пользовательской документации: оператор должен подготовить
окружение, настроить раннер, запустить прогон и прочитать отчёт —
по инструкции со скриншотами.

**Главный документ задачи: `docs/user-docs-plan.md`** — план с
структурой документов, списком скриншотов, источниками фактов и гейтами.
Следуй ему; ниже — операционные правила сессии.

## Результат сессии (артефакты)

1. `dist/БЫСТРЫЙ-СТАРТ.md` — краткая версия (1–2 экрана).
2. `dist/РУКОВОДСТВО-ОПЕРАТОРА.md` — подробная версия (разделы:
   о комплекте → как подготовить → как настроить раннер → как запускать →
   как смотреть отчёт → словарь терминов → частые проблемы).
3. ≥8 скриншотов: `docs/screenshots/*.png` + копия `dist/screenshots/`.
4. Точечные правки ссылок: `README.md`, `dist/ИНСТРУКЦИЯ.md`.
5. Heartbeat `tmp/s015/heartbeat.txt`, отчёт
   `docs/night-report-<дата>-s015.md`, продолжение —
   `docs/next-s016-prompt.md` (или финальный статус).

## T0. Pre-flight (сначала, до всего)

1. Диск C: свободно ≥10 ГБ; база `dev_erpapk_demo` доступна (COM-чек
   `t8_gate.conn_str(t.ADMIN, "")`); сеансов, кроме RAS — нет
   (`t8_gate.rac_sessions_online()`).
2. **GUI-проверка** (скриншоты требуют видимого рабочего стола):
   попробовать снять окно скриншотом (`scripts/s010_shot.py` или
   `python -c "import ctypes; print(ctypes.windll.user32.GetDesktopWindow())"`).
   - GUI доступен → путь А: реальная съёмка окон (основной).
   - GUI недоступен (headless) → путь Б: скриншоты из имеющихся
     артефактов (`docs/evidence/**`, allure-вложения прошлых прогонов,
     `tmp/**`), в тексте оставить аккуратные заглушки-каркасы
     «скриншот: <описание> (будет добавлен при интерактивной сессии)».
     НЕ рисовать картинки, НЕ выдумывать интерфейс. Это нормальный
     исход — зафиксировать в отчёте.
3. Проверить, что `dist/` собран и актуален (3 EPF + scenarios + ИНСТРУКЦИЯ;
   эталон `dist/scenarios/baseline-real.json` = 46 ключей, run-20261102-034905).

## T1. Разведка форм (фактура для текста)

- Вытащить точные названия элементов форм препроцессора и раннера из
  XML-исходников (`src/АпкПодготовкаСценарныхТестов/`,
  `src/АпкРаннер/` — формы, реквизиты, команды). В инструкции должны
  быть РЕАЛЬНЫЕ надписи кнопок и полей, не придуманные.
- Ключи настроек прогона (из ObjectModule.bsl): projectDir, templatesDir,
  coverageMapPath, v8cPath, vaEpfPath, infoBase, adminUser, adminPassword,
  timeoutMinutesPerBatch, portBase, clientType, webUrl,
  alwaysSubstitutePwd, maxTabularRows, runsBaseDir.
- Терминология — строго по словарю `docs/how-tester-works.md`
  (группа проверок, код завершения, сводка, эталон, отказная проверка).
  В скобках допустимо давать английское слово один раз при первом
  упоминании.

## T2. Скриншоты (путь А; при headless — см. T0.3)

Список — в плане (§3, ≥8 штук). Правила:

1. Снимать реальный комплект: открыть `АпкПодготовкаСценарныхТестов.epf`
   от администратора, затем `АпкРаннер.epf`; окна — фиксированного
   размера, посторонние приложения закрыть.
2. Для скриншота итоговой формы отчёта нужен короткий пробный прогон:
   **smoke-контур (00-smoke), один сценарий**. НЕ restore, НЕ dump,
   НЕ менять `tests/baseline/` и `dist/scenarios/baseline*.json`.
   Прогон — по обычной механике раннера (см. ИНСТРУКЦИЯ.md §3).
3. Все PNG — в `docs/screenshots/` с именами
   `screenshot-01-<краткое-описание>.png` … `screenshot-08-….png`;
   копия в `dist/screenshots/`.
4. Скриншоты просмотреть глазами (read tool) перед вставкой в текст:
   читаемость, правильное окно, нет мусора в кадре.

## T3. Написание документов

- Краткий (`БЫСТРЫЙ-СТАРТ.md`): чеклист требований → 4 шага → «как
  читать вердикт» (мини-скриншот формы отчёта) → «что делать, если
  красный» (ссылка на подробное руководство). Читается за 3 минуты.
- Подробный (`РУКОВОДСТВО-ОПЕРАТОРА.md`): структура — план §2. На
  основном пути НЕТ шагов с python/COM/LLM. Пишем для инженера заказчика,
  который впервые видит комплект: простыми фразами, «что нажать → что
  увидеть → что должно получиться».
- Вычитка русского текста (скилл `ru-text`): единообразие терминов,
  без канцелярита, без английских слов без перевода.
- Скриншоты в тексте — относительными путями
  (`screenshots/screenshot-0N-….png`), чтобы работало из `dist/`.

## T4. Интеграция

- `README.md`: раздел «С чего начать» → добавить ссылку на

- `dist/ИНСТРУКЦИЯ.md`: в шапку — ссылка на новое руководство оператора

- `docs/how-tester-works.md`: при необходимости — ссылка на руководство.
- Проверить ВСЕ ссылки и картинки (существование файлов, относительные
  пути).

## T5. Финал

1. Heartbeat `tmp/s015/heartbeat.txt` — по ходу сессии (ключевые шаги
   с таймстампами).
2. Отчёт `docs/night-report-<дата>-s015.md`: что сделано, скриншоты
   (список), путь А/Б (GUI), пробелы, известные проблемы (баги раннера —
   НЕ чинить, только зафиксировать).
3. `docs/next-s016-prompt.md` — продолжение (добивка скриншотов при
   пути Б, замечания по качеству).
4. **Commit+push НЕ ДЕЛАТЬ** — утром спросить пользователя
   (деструктив по правилам).

## Жёсткие правила (без изменений)

- Кириллица в bash-аргументах мангалится: русские тексты — через
  write-tool; python — `sys.stdout.reconfigure(encoding='utf-8')`;
  проверять байты, не отображение.
- 2-attempt rule: один и тот же фейл дважды → стоп, классифицировать
  (auth vs namespace vs builder vs headless vs GUI), не ретраить
  вслепую.
- Деструктив (kill процессов 1С, удаление вне tmp, commit, push,
  публикация web, правки кода/BSL/сценариев) — НЕ ДЕЛАТЬ без
  подтверждения пользователя.
- Мусор-файлы в корне репо не создавать; временные — только tmp/.
- Скриншоты — только реальные (съёмка окон или артефакты);
  графику не рисовать.
